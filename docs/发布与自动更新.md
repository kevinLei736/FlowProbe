# 发布与自动更新

这份文档说明：代码放在哪、安装包发到哪、已装的客户端怎么自动更新到新版本。

## 两个仓库，各管一件事

| 仓库 | 可见性 | 放什么 | 谁会访问 |
|------|--------|--------|----------|
| `LeiQinLin/FlowProbe` | **私有** | 源码、文档、构建脚本 | 只有开发者 |
| `LeiQinLin/FlowProbeClient` | **公开** | 每个版本的安装包与版本清单（Release 附件）| 所有使用者的客户端 |

**为什么必须拆成两个**：自动更新要能匿名下载附件。私有仓库的 Release 附件每次请求都要带令牌，
而把令牌打进客户端就等于公开这个令牌 —— 任何人解包 asar 都能拿到，它还带着对源码仓库的读权限。
所以「代码私有 + 安装包公开」是唯一站得住的组合。公开仓库里只有二进制安装包，不含任何源码。

## 更新地址在打包时决定

客户端界面里**没有**更新源设置项。地址只有一处来源：`electron-builder.yml` 的 `publish` 段。
electron-builder 打包时会把它写进安装包内的 `app-update.yml`，客户端启动时自己读。

```yaml
publish:
  - provider: github
    owner: LeiQinLin
    repo: FlowProbeClient
    releaseType: release   # 只认正式 Release，草稿与预发布不会推给所有人
    publishAutoUpdate: true
```

为什么用 `github` provider 而不是 `generic` 配一个 `releases/latest/download/` 地址：
github provider 直接读 Release 的元数据，因此 Release 正文能显示在应用的更新面板里；
而 `releases/latest/download/` 每次取文件都要穿过一层 302 跳转，部分网络环境下会让 blockmap 增量下载失效。

为什么不做成运行时可配：那等于把一件发布方只需决定一次的事，摊给每一个使用者去填。
而地址、仓库名、下载代理任何一处写错，表现都是同一个 404 —— 用户无从判断错在哪。

## 每次发新版（四步）

1. 改 `package.json` 里的 `version`（必须比线上那版高，客户端不接受降级）；
2. `npm run dist` —— 产物出在 `release/`；
3. `npm run publish:github` —— 上传到 `FlowProbeClient` 的 Release；
4. 提交代码推到 `FlowProbe`。

第 2、3 步可以合成一条：`npm run release`。

### 上传脚本需要的凭据

```ini
# 项目根目录 .env（已在 .gitignore 里，不会被提交）
DT_GITHUB_TOKEN=ghp_你的令牌
DT_RELEASE_REPO=LeiQinLin/FlowProbeClient
```

令牌在 GitHub → Settings → Developer settings → Personal access tokens 生成。
经典令牌勾 `repo` 即可（同一个令牌也用于推送私有的代码仓库）；细粒度令牌需要对发布仓库有 `Contents: read and write`。

脚本做的事：

| 步骤 | 说明 |
|------|------|
| 校验 | 令牌缺失、仓库格式不对、安装包还没打，都在动手前直接报错退出 |
| 探测仓库 | 访问不到就报「仓库不存在或令牌无权限」；**发布仓库是私有的会当场警告**，因为那样自动更新一定不可用 |
| 建或复用 Release | tag 用 `v<version>`。已存在就复用，所以上一次传到一半失败可以直接重跑 |
| 上传附件 | 同名附件先删再传（重发通常正是因为上次传坏了，跳过会把坏文件留在线上）；流式上传，不把百兆文件读进内存；自己处理重定向与重试（见下）|

上传哪些文件：

| 文件 | 必需 | 说明 |
|------|------|------|
| `latest.yml` | **是** | Windows 版本清单。**缺它的后果是静默的** —— 客户端不报错，只会一直显示「已是最新版本」 |
| `FlowProbe-Setup-x.y.z.exe` | 是 | Windows 安装包 |
| `FlowProbe-Setup-x.y.z.exe.blockmap` | 否 | 增量更新用，有则只下载变化的块 |
| `latest-mac.yml` / `.dmg` / `-mac.zip` | 否 | 在 mac 上打包后才会有。mac 的自动更新读的是 zip，不是 dmg |

## 代码推到私有仓库

```bash
git init
git add .
git commit -m "init: FlowProbe 多协议调试台"
git branch -M main
git remote add origin https://github.com/LeiQinLin/FlowProbe.git
git push -u origin main
```

`release/`（安装包）、`node_modules`、`out`、`.env` 都已被 `.gitignore` 忽略，不会进仓库。

推送时用令牌当密码（用户名填 GitHub 账号，密码粘令牌）。

不建议把令牌写进远端地址（`https://<令牌>@github.com/...`）：它会永久留在 `.git/config` 里，
那个文件虽然不进仓库，但任何能读这台机器的人都看得到，且 `git remote -v` 会直接把它打在屏幕上。

### 首次推送踩到的两个坑（实测）

| 现象 | 原因与处置 |
|------|-----------|
| `git push` 报 `Failed to connect to github.com port 443` | 国内到 github.com 的连通性是**间歇性**的，同一条命令连试五次可能全失败、下一分钟又通。`api.github.com` 与 `raw.githubusercontent.com` 往往还是好的，所以「API 能用」不代表「git 能推」。处置：加重试循环，别急着换代理 |
| 走 `gh-proxy.com` / `ghfast.top` 之类的镜像推送报 `Invalid username or token` | 这类镜像只代理**匿名读**（下载 raw 文件、克隆公开仓库），不转发 Git 的认证。推送必须直连 github.com |

`GIT_TERMINAL_PROMPT=0` 值得设上：认证失败时 git 会弹交互式凭据对话框，在脚本或无终端环境里会挂住，
设成 0 让它直接失败返回。

## 换成自建服务器（备用方案）

国内网络访问 github.com 常常超时。如果目标用户网络受限，把 `publish` 段换成静态目录即可：

```yaml
publish:
  - provider: generic
    url: https://你的服务器/flowprobe/
    publishAutoUpdate: true
```

服务端只要能按路径返回文件（Nginx、对象存储、内网文件服务都行），把 `release/` 下那三个文件拷进去，
不需要任何服务端程序。客户端两种 provider 都认，换完重新打包即可。

## 验证升级路径（发版前值得跑一次）

「检查更新说已是最新」只能证明清单读到了，证明不了升级真的能走通。想完整验一遍：

1. 把当前 `release/win-unpacked/` 整个拷到别处留一份，这就是「旧客户端」；
2. 改 `package.json` 的版本号（补丁位 +1 即可），`npm run release`；
3. 运行留下来的那份旧客户端，等约 8 秒（启动自查有延迟），打开「帮助 → 检查更新」。

正常应当看到：发现新版本 → 显示这一版的发布说明 → 点下载走完进度条 → 按钮变成「重启并安装」。

下载下来的安装包在 `%LOCALAPPDATA%\flowprobe-updater\pending\`，同目录的 `update-info.json` 里记着它的 sha512，
可以和 `release/latest.yml` 里的值对一下 —— 两处一致说明下载完整，安装不会在校验环节失败。

## 排查

| 现象 | 原因 |
|------|------|
| 上传附件报 `HTTP 307` | 已在脚本里处理：请求体是流，只能消费一次，`fetch` 内置的跟随重定向拿不到可重放的 body。脚本改为手动重发（每次新开一个流）。若仍反复出现，检查是不是网络中间设备在改写请求 |
| 上传中途断开 | 脚本会自动重试 4 次（退避 2/4/6 秒）。全失败就直接重跑 `npm run publish:github`，Release 会被复用、同名附件先删再传 |
| 「发布仓库里还没有正式版本」 | `FlowProbeClient` 里一个 Release 都没有，或只有草稿/预发布。跑一次 `npm run publish:github` |
| 一直显示「已是最新版本」 | Release 附件里没有 `latest.yml`，或里面的版本号不高于本机版本 |
| 「找不到版本清单」 | 附件被删了或名字被改过 |
| 下载到一半报「校验不通过」 | 附件与 `latest.yml` 记录的校验值不符，多半是上传时断了。重新跑发布脚本覆盖 |
| 能检查到但下载 404 | 附件名与清单里记的不一致。产物名已固定为不含空格的纯 ASCII 正是为了避免这一点，别手动改名 |
| 检查更新一直转圈或超时 | 目标用户访问不了 github.com。这在国内是常态且**间歇性**的，重试往往就好；长期不通就换自建服务器（见上一节）|
| 「发布方尚未启用更新服务」 | 装的是 1.20.0 及更早的包，那些包里写的还是占位域名。装一次新版即可 |
| 「这个安装包没有内置更新地址」 | 打包时 `electron-builder.yml` 里没有 `publish` 段 |
| 源码运行时说「开发运行不检查更新」 | 正常。`npm run dev` 下没有 `app-update.yml`，只有安装版才检查 |
