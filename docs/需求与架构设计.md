# 探流 FlowProbe — 设计与需求文档

> 版本：v0.1（草案）
> 定位：一款面向嵌入式 / 网络 / 物联网开发者的「多协议网络与串口调试台」。
> 交互与视觉语言参考 Codex 桌面版：深色为主、克制的留白、单色强调色、等宽字体承载报文数据、左侧导航 + 中间会话 + 右侧检查器的三栏结构。

---

## 1. 产品概述

### 1.1 目标
把开发者日常最常用的连接调试能力集中到一个桌面工具里，覆盖：
- TCP（Socket）客户端 / 服务端
- WebSocket 客户端 / 服务端
- UDP 客户端 / 服务端（含广播与组播）
- 串口（Serial / COM）连接
- HTTP Mock 服务（模拟 API 后端接口）
- HTTP 接口测试工具（API Client）

统一的「连接 / 请求 → 发送 → 接收 → 观察」工作流，配合每种协议的常规参数设置，并提供数据格式化、日志、脚本化 Mock 与接口断言等增强能力。

### 1.2 目标用户
- 嵌入式 / 硬件工程师（串口、TCP 透传模组调试）
- 后端 / 物联网工程师（协议联调、压力自测、Mock 上下游）
- 测试工程师（构造异常报文、回归脚本）

### 1.3 设计原则
- 单窗口多会话：每个连接是一个「会话 Tab」，可并行运行、互不干扰。
- 数据优先：报文收发区是界面主体，HEX / 文本双视图随时切换。
- 可复现：连接配置、发送片段、自动应答规则均可保存为「预设」并导入导出。
- 非阻塞：所有 IO 在后台进程执行，界面永不卡死。

## 2. 技术架构

### 2.1 技术选型（语言与框架）

| 层 | 选型 | 说明 |
|----|------|------|
| 桌面外壳 | **Electron** | 需要 Node 原生能力（原始 TCP、串口）；跨平台 Windows / macOS / Linux |
| 前端 UI | **React 18 + TypeScript** | 组件化、类型安全，契合 Codex 风格的现代前端栈 |
| 构建 | **Vite + electron-builder** | 快速热更新，一键打包安装程序 |
| 状态管理 | **Zustand** | 轻量，适合多会话状态 |
| UI 组件 | **自研设计系统 + Radix Primitives** | 深色主题、无障碍、可控样式 |
| 样式 | **Tailwind CSS + CSS 变量主题** | 令牌化的颜色 / 间距，方便统一风格 |
| 图表 | **原生 SVG 自绘** | 实际未引入图表库：看板与数值曲线的图形都是纯函数产出 SVG，省掉一个重依赖，也便于跟随主题令牌换色 |
| 通信内核 | **Node.js 主进程** | net（TCP）、ws（WebSocket）、serialport（串口）、http/https（HTTP Mock 服务与接口测试客户端） |
| HTTP 内核 | **内置 http/https + 轻量路由** | HTTP Mock 服务端路由匹配；接口测试基于 Node 原生请求（或 undici） |
| 持久化 | **SQLite（better-sqlite3）+ JSON 预设文件** | 历史日志入库，预设可读可导出 |
| 脚本引擎 | **Node vm / isolated-vm 沙箱** | HTTP Mock 动态响应脚本的安全执行 |

> 备选：若要更小体积与更好性能，可将外壳换为 **Tauri（Rust）**，通信内核用 Rust 的 `tokio` / `tokio-tungstenite` / `serialport-rs`。本文档默认采用 Electron 方案以降低实现门槛，架构分层保持不变，便于后续替换。

### 2.3 统一连接抽象

所有协议实现同一个适配器接口，UI 与内核通过统一事件模型交互：

```ts
interface ConnectionAdapter {
  id: string;
  kind: 'tcp-client' | 'tcp-server' | 'ws-client' | 'ws-server' | 'serial'
      | 'http-mock' | 'http-test'
      | 'mqtt-client' | 'modbus-tcp' | 'modbus-rtu';   // M22
  start(config): Promise<void>;
  stop(): Promise<void>;
  send(frame: OutgoingFrame, target?: PeerId): Promise<void>;
  // 事件：status / data / peer-connected / peer-disconnected / error / metrics
  on(event, handler): void;
}
```

事件统一为 `SessionEvent`，携带时间戳、方向（TX/RX）、对端标识、原始字节与解码文本，供 UI 渲染与日志入库。

**这层抽象是后续协议扩展的复用点。** 新协议只要把收发映射成 Frame（协议专属信息放 `meta`，如 MQTT 的 `topic/qos/retain`、Modbus 的 `funcCode/startAddr`），就能自动继承报文时间轴、虚拟滚动、HEX/文本切换、过滤高亮、历史落库、全局搜索、看板吞吐统计、录制回放这一整套既有能力，无需改动上层。这也是 M22 选择自研 Modbus 编解码、而 MQTT 复用 `mqtt` 包的判断依据——前者要精确控制字序与判帧才能塞进这套抽象，后者的传输层差异已被库内部吸收。

## 3. 功能模块需求

### 3.1 会话与工作区（通用）
- 多会话 Tab，支持并行连接；Tab 显示协议图标、连接状态灯（灰/黄/绿/红）。
- 三栏布局：左=会话/预设导航，中=报文收发，右=当前会话设置/检查器。
- 会话可命名、复制、导出配置；工作区（多个会话集合）可整体保存/加载。
- **会话持久化（已实现）**：会话列表自动落盘到用户数据目录的 `workspace.json`，应用重启后按原 id 完整恢复；支持就地改名、修改连接参数（停旧适配器→重建）、勾选「下次打开自动连接」、一键清空工作区。写入采用「临时文件 + 原子改名」，强杀进程不会损坏配置。
- **持久化边界**：只存配置（id/kind/name/config/autoStart/createdAt），不存报文与运行指标，避免文件无限增长。恢复时先重建全部会话再统一启动自启会话，避免端口竞争。
- 全局深色/浅色主题；强调色可选。

### 3.2 数据收发显示（通用核心）
- **断线重连策略（已实现）**：TCP 客户端、WebSocket 客户端、串口共用一套指数退避器 `Backoff`。等待时长 = `min(base * 2^n, max)`，叠加最多 20% 负向抖动避免多会话同时重连；连接成功后立即 `reset()`；`maxAttempts > 0` 时用尽后停止并将会话置为 error；手动停止不触发重连。可配 `reconnectIntervalMs`（首次等待，默认 1000）、`reconnectMaxIntervalMs`（封顶，默认 30000）、`reconnectMaxAttempts`（0=不限）。
- **连接生命周期日志（已实现）**：Frame 新增 `level`（info/success/warn/error）与 `conn` 标记。适配器通过 `emitConn()` 记录连接建立、断开、重连预告、放弃重连、客户端接入与断开，界面按级别着色并支持「仅连接日志」筛选。
- 收发一体的时间轴视图，TX/RX 用颜色与方向箭头区分。
- 显示格式切换：**HEX**、**ASCII/UTF-8**、**Base64**、混合（HEX+可打印字符）。
- 每条报文显示：序号、时间戳（可选毫秒/微秒）、方向、对端、字节数、内容。
- 发送区：多行输入，格式选择（文本/HEX），支持转义（\r\n \xNN）、追加结束符（CR/LF/CRLF/自定义）。
- 快捷发送片段（Snippets）：常用报文一键发送，支持命名、分组、导入导出。
- 循环发送：按间隔重复发送、发送次数、序列脚本。
- 接收控制：自动滚动开关、暂停、清屏、按关键字/正则过滤、高亮匹配。
- 分帧策略：按固定长度 / 分隔符 / 头长域（length-prefixed）/ 超时静默 分包，解决 TCP/串口粘包。
- **协议解析模板（已实现）**：为自定义二进制协议定义帧结构，报文行可就地展开为字段表。字段类型覆盖 uint8/16/32、int8/16/32、float32/64、HEX 串、ASCII、BCD、位图；多字节可选大小端；数值支持倍率+偏移的工程值换算、单位与枚举映射（如 `1=读取`）。尾部校验支持和校验、异或校验、CRC16-Modbus，校验范围为首字节至校验位之前，结果以通过/不符标签呈现。模板可按 HEX 前缀与收发方向匹配，`auto` 模式按前缀长度择优。解析对半包容错：字节不足时保留已解析字段并标注「字节不足」，不整体失败。解析在渲染层按可视行惰性执行，配合虚拟滚动不影响高吞吐性能。
- 收发统计：字节数、帧数、速率（B/s）、错误计数。
- 日志导出：TXT / CSV / 二进制 dump。
- **报文录制与回放（已实现）**：把时间轴上的报文（含当前过滤结果）打包成版本化 JSON，存相对时间以保证任何时候回放都复现原始节奏。回放由渲染层 `ReplayPlayer` 调度，采用「追赶应到时刻」而非固定间隔累加，避免长录制的定时器抖动累积误差；同一时刻的多帧一次性吐出，低倍速下不丢帧。回放帧经 `injectFrame` 复用真实报文的 rAF 合批通道注入，带 `replay` 标记且**不触发真实链路发送**。支持 0.25×–10× 变速（变速前先结算已走过的录制内时间）、暂停/继续/重播/停止，控制条卸载时强制 dispose 定时器。

### 3.3 TCP（Socket）客户端
- 设置：目标 IP/域名、端口、连接超时、自动重连（间隔/次数）、Keep-Alive、Nagle（TCP_NODELAY）、本地绑定端口。
- 功能：连接/断开、发送/接收、心跳包（内容+间隔）、断线自动重连。

### 3.4 TCP（Socket）服务端
- 设置：监听地址/端口、最大连接数、backlog、按客户端粘包策略。
- 功能：客户端连接列表（IP:Port、连接时长、收发统计），可对单个/全部客户端发送（广播），踢出指定客户端，白/黑名单。

### 3.5 WebSocket 客户端
- 设置：ws/wss URL、子协议（Sub-Protocol）、自定义 Header、Origin、TLS 校验开关、Ping 间隔、重连策略。
- 功能：文本帧/二进制帧发送、Ping/Pong 观测、关闭码与原因显示、握手过程查看。

### 3.6 WebSocket 服务端
- 设置：监听端口、路径（Path）、是否 wss（证书/私钥）、子协议、最大连接、心跳。
- 功能：客户端列表与广播、单播、按路径分组、握手信息查看、异常关闭码下发。

### 3.7 串口连接
- 设置：串口号（自动枚举 + 热插拔刷新）、波特率（含自定义）、数据位、停止位、校验位、流控（None/RTS-CTS/XON-XOFF）、DTR/RTS 电平控制。
- 功能：打开/关闭、收发、HEX/文本、行结束符、发送延时；断开检测与自动重连；线路状态（CTS/DSR/RING/CD）显示。

### 3.8 HTTP Mock 服务（模拟 API 服务器）
> 定位修正：Mock 的核心场景是**模拟 HTTP 后端接口**——在本地起一个 HTTP(S) 服务，按路由规则返回可配置的响应，供前端/移动端/联调方在真实后端未就绪时对接。它是一个独立的会话类型（`http-mock`），而非 TCP/串口的字节回声。

- **服务实例**：可创建多个 HTTP Mock 服务，各自监听独立端口；支持 HTTP 与 HTTPS（自签或导入证书）、可配 base path、全局 CORS 开关与自定义响应头。
- **路由规则（Route）**：每条规则定义
  - 匹配：HTTP 方法（GET/POST/PUT/DELETE/PATCH/OPTIONS/HEAD/ANY）、路径（精确 / 通配 `*` / `:param` 占位 / 正则）、可选按 Query、Header、Body（JSON 字段/正则）进一步筛选；支持优先级排序与首个命中。
  - 响应：状态码、响应头、响应体（JSON / 文本 / XML / 二进制 / 从文件读取）、`Content-Type`。
- **动态响应**：
  - **模板**：在响应体中插入 `{{path.param}}`、`{{query.x}}`、`{{body.field}}`、`{{header.x}}`、`{{now}}`、`{{uuid}}`、`{{randomInt}}`、`{{sequence}}` 等占位符，实现回显与动态数据。
  - **脚本模式**：在沙箱中运行 JS，`handler(req, res)` 可读取 `req.method/path/params/query/headers/body`，自定义 `res.status/headers/body`，用于条件分支、鉴权校验、依赖上游数据的动态返回。
  - **数据模拟**：内置随机数据生成（姓名、邮箱、时间、序列、UUID、数组批量），便于造列表/分页数据。
- **有状态 Mock**：可维护内存态数据集（如简易 REST 资源 `/users`），支持基于请求增删改查形成"可读写的假后端"；场景重置一键清空。
- **场景库（Scenario，已实现）**：同一批路由可挂多个场景，顶部下拉与命令面板均可一键切换，切换后立即生效。场景采用**字段级覆盖**（`overrides: Record<routeId, {enabled?, respStatus?, bodyType?, respBody?, respHeaders?, delayMs?, mode?, script?}>`），只覆盖显式声明的字段，未声明字段沿用路由原始配置；覆盖在筛选 `enabled` 之前叠加，因此场景可临时禁用某条路由使其走「未命中」分支。场景可自带 `fault` 故障注入参数并覆盖全局设置。内置「登录过期 401 / 服务不可用 500 / 慢接口 3s / 接口未上线 404」四个场景；命中场景的请求会在日志行与详情中标注场景名。
- **故障注入**：按概率返回指定错误码、注入响应延迟、随机超时、限流（429），用于客户端健壮性测试。
- **代理透传（可选）**：未命中的路由可转发到真实后端（proxy pass），实现"部分接口 Mock、其余走真实"，并可录制真实响应回填为 Mock。
- **请求日志**：实时列出收到的请求（方法、路径、状态、耗时、命中规则），可展开查看请求/响应完整报文，支持按路径/状态过滤与导出。

### 3.9 HTTP 接口测试工具（API Client）
> 面向接口联调/回归的请求构造与验证工具，与 HTTP Mock 服务互补：一个"造服务端"，一个"发客户端请求"。

- **请求构造**：
  - 方法：GET/POST/PUT/DELETE/PATCH/OPTIONS/HEAD。
  - URL：地址栏 + Query 参数表（键值对可勾选启用）；支持路径变量。
  - Header：键值对编辑，常用头快捷补全（Content-Type、Authorization、UA 等）。
  - Body：none / raw（JSON、文本、XML，带语法高亮与格式化）/ x-www-form-urlencoded / form-data（含文件上传）/ 二进制。
  - 认证：无 / Basic / Bearer Token / API Key（Header 或 Query）。
- **响应查看**：状态码与状态文本、耗时、响应大小；响应体 JSON 美化/折叠、原始文本、HEX、图片/二进制预览；响应头与 Cookie 列表；重定向链路查看。
- **环境与变量**：环境（dev/test/prod）与变量管理，`{{baseUrl}}`、`{{token}}` 等占位符在 URL/Header/Body 中替换；支持全局变量与临时变量。
- **集合与历史**：把请求保存到集合（Collection）分组管理，支持导入导出；自动保留请求历史，可一键重放。
- **断言与测试**：对响应做断言（状态码、响应时间阈值、JSONPath 字段值、包含文本、正则、Schema 校验）；结果以通过/失败标记。
- **批量与串联**：集合可顺序执行（Runner），支持从上一步响应提取变量传递到下一步（如登录取 token 供后续请求）；输出批量测试报告。
  - **变量提取规则**：从响应体 JSON 路径（`data.token`、`list[0].id`）、响应头（如 `set-cookie`）或状态码取值，写入指定变量名；单次发送时同步回写当前环境，批量运行时进入运行时变量池。
  - **Runner 执行控制**：勾选参与的请求、上下调整执行顺序、设置请求间隔、失败即停止（后续请求标记为"跳过"）。
  - **报告**：统计用例通过数、断言通过数、跳过数与总耗时；逐条展示状态码/耗时/大小/断言明细/提取结果；可导出 Markdown（表格 + 明细）或 JSON（原始结构，便于接入 CI）。
- **其他**：cURL 导入/导出、代码片段生成（fetch/axios/cURL）、TLS 校验开关、超时与重试、代理设置、gzip/br 自动解压。

### 3.10 建议补充的增强功能
- **内置校验工具**：CRC8/16/32、LRC、Checksum、MD5/SHA，可作为发送模板函数。
- **编解码助手**：字节序（大小端）转换、进制转换、时间戳互转、URL/Base64/JSON 格式化。
- **协议解析插件**：可为特定业务协议编写解析器，把原始字节渲染成字段表（TLV / 自定义帧头）。
- **数据可视化（已实现，见 3.12）**：从报文中按规则提取数值绘制实时曲线，并提供跨会话的全局看板。
- **命令面板（⌘/Ctrl+K）**：Codex 风格的全局命令入口。模糊匹配（按序命中字符、连续命中加权、前缀与子串额外加分），按组展示：跳转会话（可搜会话名/协议/主机/端口/串口号）、操作（新建连接、接口测试、工具箱、数据看板）、当前会话（启动或停止、复制、切换自动连接、清空报文、删除）、分组（移动到分组、移出分组）、标签（按标签筛选、清除筛选）、协议解析、Mock 场景、界面（切换左侧栏与检查器、三档主题）。↑↓ 选择、Enter 执行、Esc 关闭。
- **快捷键体系**：发送（Ctrl+Enter）、清屏、切换视图、暂停接收等。

### 3.11 会话分组与标签

**需求背景**：会话数量上去之后，左栏变成一条长列表，靠肉眼找会话的成本随数量线性上升。分组解决「按项目收纳」，标签解决「按维度横切」，两者正交可叠加。

**分组**
- 每个会话有一个可选的 `group` 字段，空字符串表示未分组。
- 左栏按分组渲染，分组标题可折叠，标题右侧显示该组会话数。具名分组按名称排序（`localeCompare` 中文序），「未分组」恒排最后。
- 检查器提供分组输入框（回车或失焦提交）+ 已有分组名快捷 chip，避免用户重复手打或写错。
- 命令面板提供「移动到分组：XXX」「移出分组」命令。
- 复制会话时携带 group 与 tags，副本天然落在同一组。

**标签**
- 每个会话有 `tags: string[]`，主进程侧统一 trim 并去重后落盘。
- 标签输入支持一次录入多个，分隔符为英文逗号、中文逗号与空白。
- 左栏标签条按使用次数降序排列（次数相同按名称），点击切换筛选。
- 多标签筛选取**交集**语义：标签常用来叠加维度（项目 + 环境），交集才符合直觉。
- 折叠状态与标签筛选写入 localStorage `toolbox.sessionOrg`；筛选关键字仅内存态，不持久化（每次打开应看到完整列表）。

**关键词筛选**：单一输入框同时匹配会话名、分组名、标签、host、url、serialPath、port，与标签筛选叠加。

**IPC 契约**：新增 `session:setMeta`，入参 `(id, SessionMetaPatch)`。该操作只改内存态并落盘，**不重建适配器、不中断运行中的连接**，因为分组标签属于组织信息而非链路参数。

### 3.12 数据可视化看板

**定位划分**：单会话的协议字段曲线归会话视图（见 M15）；看板回答全局问题——哪些链路在跑、谁在刷流量、包长分布是否异常、Mock 的错误率与响应耗时如何。

**统计范围**
- 作用域：全部会话 / 单个分组 / 单个会话（下拉切换）。
- 左栏标签筛选对看板同样生效，看板顶部另有标签条可直接切换。
- 时间窗口三档：60s / 180s / 600s。

**指标卡（6 个）**：实时发送速率、实时接收速率、报文速率、在线连接数、Mock 错误率、响应 P95。速率取最近 5 个完整时间桶的均值（单桶抖动过大不适合直接展示）；错误率 > 10% 标红。

**图表（6 块，均为原生 SVG）**

| 图表 | 数据来源与算法 |
|------|----------------|
| 吞吐趋势 | `bucketize()` 按 1 秒桶聚合 TX/RX 字节，空桶补零，双序列面积 + 折线 |
| 会话状态 | `statusSlices()` 统计六种状态，环图（stroke-dasharray 拼接） |
| 报文长度分布 | `sizeHistogram()` 按 8/32/64/128/256/512/1K/1.5K 分档 |
| 流量最高的会话 | 按 metrics 累计收发字节排序，点击行跳转该会话 |
| 分组流量对比 | `groupStats()` 按分组累计字节，未分组归入「未分组」 |
| Mock 状态码分布 / 热门接口 | `statusCodeSlices()` 按状态码族聚合；`topPaths()` 统计 method+path 命中次数与错误占比 |

**性能与算法取舍**
- 不引图表库：数据已在聚合阶段收敛到百量级，手写 path 字符串比多一个依赖划算，且配色可直接吃主题令牌。
- 桶聚合从最新报文倒序回扫，遇到窗口外时间戳立即 break，不做全量遍历。
- 图表按 1 秒节拍重算（`setInterval` + tick state），刷新频率与报文吞吐解耦。
- 耗时统计给 P50 与 P95 而非仅均值：均值会被个别慢请求拉高，P95 才描述「大多数请求有多慢」。
- 空桶显式补零，静默期在折线上表现为落到零线而非连成斜线。

**导出**：当前窗口的吞吐序列导出 CSV（时间、发送字节、接收字节、发送帧、接收帧）。

### 3.13 报文历史（SQLite 落库）

**定位划分**：内存时间轴解决「现在在发什么」（关掉即失），看板解决「最近十分钟整体如何」，历史库解决「上周三那台设备发过什么」——跨重启的可检索归档。

**落库范围**
- 报文（frames）：所有 TX/RX/system 帧，含连接生命周期日志。
- HTTP 请求（http_logs）：HTTP Mock 的每次请求与响应。
- 回放注入的帧（`replay === true`）不入库：它不是真实链路数据，混入会污染排查结论。

**表结构与索引**

| 表 | 关键列 | 索引 |
|----|--------|------|
| frames | id、session_id、session_name、session_kind、session_group、ts、direction、size、encoding、raw_base64、text、peer_label、level、conn | (ts)、(session_id, ts)、(direction, ts) |
| http_logs | id、session_id、session_name、ts、method、path、query、status、duration_ms、req_body、resp_body、matched_route、scenario | (ts)、(session_id, ts)、(status, ts) |
| meta | key、value | 主键 key（存 HistoryConfig 的 JSON） |

会话名/类型/分组在写入时冗余进行：会话删除后历史依然可读，也免掉查询期的 JOIN。

**写入策略**
- 驱动选 better-sqlite3（同步 API）：写入发生在主进程，批量事务比异步回调开销更低；Electron 31 内置 Node 20 尚无 `node:sqlite`。
- WAL 模式；攒够 200 条或空闲 800ms 落一次盘，整批用 `db.transaction()` 包住。高频报文逐条写会把磁盘打满。
- 每次查询/统计前先 `flush()`，否则刚发的报文查不到，会被误判成丢数据。
- 写失败时丢弃当前批并记录 failure，避免坏数据反复重试堵死队列。

**清理策略**
- 按天：`DELETE ... WHERE ts < cutoff`，启动时与改配置时各跑一次。
- 按条数：先 `SELECT id ... LIMIT 1 OFFSET excess` 取阈值，再 `DELETE WHERE id < ?`。走主键索引，比 `ORDER BY ... LIMIT` 子查询快得多。
- 手动：压缩数据库（VACUUM）、清空全部、按会话删除。

**检索能力**
- 报文：会话（多选，含已删除会话）、时间区间、方向、仅连接日志、关键字 LIKE、字节数上下限、升降序、分页（默认每页 200）。
- HTTP：会话、时间区间、状态码族（2/3/4/5xx 多选）、方法、关键字、最小耗时、分页。
- WHERE 条件全部参数化拼接，筛选值不进 SQL 字符串。

**导出**：按当前筛选导出 CSV，上限 5 万行。查询与序列化都在主进程完成（十万行对象经 IPC 搬到渲染层再拼字符串是纯浪费），文件带 UTF-8 BOM。

**容量可视**：库概况给报文数、HTTP 数、会话数、文件字节数（主库 + `-wal` + `-shm` 三个文件合计，否则 WAL 未 checkpoint 时会一直显示 4KB）、最早/最新时间、近 14 天每日条数、按会话占用排行。

### 3.14 全局搜索（跨会话跨表检索）

**定位划分**：历史页的多维筛选服务于「我知道去哪儿找」；全局搜索服务于「只记得一个订单号/错误码，不知道它在哪个会话哪一天」。二者共用同一份 SQLite 库，入口与心智模型不同。

**功能需求**
- 入口：`Ctrl+F` 全局快捷键、左栏「全局搜索历史」按钮、命令面板同名命令。
- 一次查询同时打 `frames` 与 `http_logs` 两张表；HTTP 侧覆盖 path、query、请求体、响应体。
- 输入防抖 260ms；并发结果按序号丢弃过期响应，避免慢查询覆盖新查询。
- 作用域两档：默认「最近 5 万条」，可切「全部历史」；另可用会话下拉限定范围。
- 命中片段带上下文（前后各 40 字符，整体上限 220 字符）并高亮关键字。
- 结果按时间倒序交织两类来源；按会话聚合为可点击 chips，点击即收窄。
- 状态条给出「命中数 · 显示数 · 扫描行数 · 耗时」，慢查询与空结果可辨。
- 键盘导航：`↑`/`↓` 选中、`Enter` 跳转历史页（携带关键字与会话，历史页行内同样高亮）、`Esc` 关闭。

**检索实现取舍：LIKE + 扫描上限，不用 FTS5**

在 30 万行报文库上实测两条路线：

| 方案 | 搜索耗时 | 索引开销 | 写入放大 |
|------|---------|---------|---------|
| `LIKE` 全表扫（罕见词命中） | 65ms | 0 | 无 |
| `LIKE` 全表扫（无命中，最坏） | 68ms | 0 | 无 |
| `LIKE` + 限定最近 5 万条 | 6ms | 0 | 无 |
| FTS5 虚拟表 + 同步触发器 | ~0ms | +13MB | 插 2 万行 1558ms vs 83ms，约 19 倍 |

结论：**选 LIKE**。报文库写多读少（每秒可能落几百条，搜索每天几次），为偶发查询把常态写入吞吐压到十九分之一不划算，且 FTS5 触发器还会放大库体积与迁移复杂度。`scanLimit` 用 `id > MAX(id) - N` 裁剪，走主键索引，最坏情况仍在几十毫秒量级。

**编码等价匹配**
`frames.text` 存的是按会话显示编码渲染后的文本，同一条 `ALARM` 在 TEXT 会话里是 `ALARM`、在 HEX 会话里是 `414c41524d`，直接 LIKE 会漏掉一半。因此关键字会自动扩展为等价模式集合：
- 输入普通文本（含中文，长度 ≥2）→ 附加其 UTF-8 十六进制形式（`温度` → `e6b8a9e5baa6`）。
- 输入疑似十六进制串（纯 hex、偶数长度、≥4 位）→ 附加解码后文本，仅当解码结果全为可见 ASCII 时采用（否则如 `00ff00ff` 会产生噪声模式）。
- 片段定位逐个试模式取首个命中，高亮长度按实际命中模式计算，否则 HEX 命中只会高亮一半。

**注入与通配符安全**
- 关键字全部参数绑定，不进 SQL 字符串。
- `\`、`%`、`_` 显式转义并声明 `ESCAPE`，搜 `%` 得到的是真正含百分号的报文而非全库。（实现踩坑：JS 里多写一层反斜杠会让 SQLite 报 `ESCAPE expression must be a single character`，且所有带关键字的查询静默返回 0 条。）


### 3.15 MQTT 客户端（已实现 · M22）

**为什么要做**：工控与 IoT 场景里 MQTT 的出现频率已经接近裸 TCP。现在用户要调 MQTT 设备只能拿 TCP 客户端硬啃 CONNECT 报文，等于没有支持。

- **连接设置**：Broker 地址（mqtt / mqtts / ws / wss 四种 scheme）、端口、Client ID（默认随机且可锁定）、用户名密码、Keep-Alive、Clean Session / Clean Start、协议版本（3.1.1 / 5.0）、连接超时、自动重连（复用现有指数退避）。
- **TLS**：CA / 客户端证书与私钥路径、是否校验服务端证书、SNI 覆盖。
- **遗嘱消息（Will）**：主题、载荷、QoS、Retain。
- **订阅**：多条订阅并存，每条含主题过滤器（支持 `+` / `#`）、QoS 0/1/2、订阅开关。订阅列表随会话落盘。
- **发布**：主题、载荷（文本 / HEX / JSON）、QoS、Retain、MQTT 5 的 User Properties 与 Content Type、响应主题与关联数据。
- **收发显示**：复用报文时间轴，行首额外展示主题与 QoS 徽标；主题可点击加入过滤。
- **MQTT 5 增强**：订阅标识符、原因码与原因字符串显示（`SUBACK` / `PUBACK` / `DISCONNECT` 的失败原因要能看见，这是 5.0 相比 3.1.1 最实用的一点）。
- **主题树视图**：按 `/` 层级把收到的主题聚合成树，每个节点显示最近载荷与消息计数，解决「不知道设备到底往哪些主题发」的问题。

**实现取舍**：主进程用 `mqtt` 包（同时支持 TCP 与 WebSocket 传输，省掉自己写 WS 桥接）。会话类型新增 `mqtt-client`，走现有 `SessionAdapter` 抽象，收发映射为 Frame（`meta.topic` / `meta.qos` / `meta.retain`），因此历史落库、全局搜索、看板吞吐统计**零改动自动生效**。

**落地记录（M22）**：

- 库自带的自动重连与自动重订阅**全部关闭**（`reconnectPeriod: 0`、`resubscribe: false`），改走项目统一的指数退避 `Backoff`。两套重连机制并存会互相打架，而且库内重连不会经过我们的连接生命周期日志，断线记录会缺失。
- 订阅表改动走 `mqttUpdateSubs` 增量下发，只做差集订阅/退订，不断链路；连接参数改动才触发重建。界面上用两个不同按钮把这个区别讲清楚。
- Broker 授予的 QoS 会校验：≥128 视为拒绝并明确报出，不再让用户以为订上了却收不到消息。
- 载荷展示方式按内容判断（控制字符占比 < 10% 走 UTF-8，否则走 HEX），避免二进制载荷把时间轴刷成乱码。
- **主题树视图暂缓**：时间轴上的主题徽标已支持点击即按主题过滤，覆盖了「不知道设备往哪些主题发」的主要场景；独立主题树的增量价值有限，留到 M23 与多标签页一起做。

### 3.16 Modbus 主站（TCP / RTU）（已实现 · M22）

**为什么要做**：协议解析模板里已经内置了 CRC16-Modbus 校验，说明用户场景就在 Modbus 上，但目前仍要手工拼 `01 03 00 00 00 0A` 再手算 CRC。做成寄存器表后效率差一个量级。

- **传输层两档**：Modbus TCP（MBAP 头，事务标识自增）与 Modbus RTU（串口，CRC16 + 3.5 字符静默间隔判帧）。RTU over TCP 作为第三档兼容工控网关。
- **设置**：从站地址（Unit ID）、响应超时、重试次数、请求间隔（防止从站被打爆）、字节序与字序（大端 / 小端 / 字交换，工控设备这里差异极大，必须可配）。
- **功能码**：`01` 读线圈、`02` 读离散输入、`03` 读保持寄存器、`04` 读输入寄存器、`05` 写单线圈、`06` 写单寄存器、`0F` 写多线圈、`10` 写多寄存器。
- **寄存器表（核心界面）**：用户维护一张点表——名称、功能码、起始地址、数量、数据类型（uint16 / int16 / uint32 / int32 / float32 / float64 / bits / string）、倍率、偏移、单位、读写权限、备注。表格直接显示实时值，可就地写入。
- **周期轮询**：每个点位可设轮询间隔，主站自动把地址连续的点位**合并成一次批量读**（相邻地址间隔小于阈值就并到同一请求），减少往返。
- **异常码解析**：把 `0x81`–`0x90` 的异常响应翻译成中文（非法功能码 / 非法数据地址 / 非法数据值 / 从站设备故障 / 确认 / 从站设备忙 / 存储奇偶性差错 / 网关路径不可用 / 网关目标无响应），不再让用户查表。
- **与既有能力衔接**：点表读出的数值字段自动可勾选进**数值曲线**；每次请求响应都落**报文历史**，方便事后追现场问题。

**实现取舍**：不引入第三方 Modbus 库。协议本身极简（PDU 最长 253 字节），自己实现可以精确控制字序、超时与半包，避免第三方库把 CRC 和字序策略写死。RTU 复用现有串口适配器与分帧模块。

**落地记录（M22）**：

- 编解码独立成 `src/main/modbus/pdu.ts` 纯函数层（CRC16 查表、PDU 构造与解析、字序换算、批量读计划），与传输层解耦，便于单独验证。
- 请求**串行排队**，队列间隔 `gapMs`。Modbus 是一问一答协议，并发请求会让从站丢包，这不是性能优化而是正确性要求。
- 判帧双保险：TCP 按 MBAP 长度域切；RTU 先按功能码推算期望长度，再叠加 3.5 字符静默超时兜底，防止从站返回异常响应（长度与正常响应不同）时卡死。
- 事务号不匹配的响应直接丢弃并记日志，而不是错配给上一个请求——错配会导致数值张冠李戴，比丢一帧危险得多。
- 界面上实时值与原始寄存器 HEX **并排显示**。32 位量字序不对时工程值会是个离谱的数，但 HEX 是正常的，两者对照能立刻判断是字序问题还是地址错了。
- 类型切换时自动把数量对齐到该类型的固定字长（float32 → 2、float64 → 4），减少一类常见配置错误。
- Modbus 会话的收发编辑器与时间轴默认按 HEX 显示（其他协议仍默认 UTF-8）。纯二进制协议按文本渲染只会得到一串控制字符，默认值应该跟着协议走。

**顺带修掉的一个既有缺陷**：报文合批原来只挂 `requestAnimationFrame`。窗口最小化或被完全遮挡时浏览器会挂起 rAF 回调，报文全部堆在缓冲区进不了时间轴，切回前台才一次性刷出来——长时间挂机抓包时看起来像丢数据。现在 rAF 与 120ms 定时器**同时挂，谁先到谁刷**：前台保持按帧节流的渲染性能，后台由定时器接管保证数据可见。这个问题在 MQTT/Modbus 上才暴露，是因为它们是本轮第一批「不需要人工操作就持续产生报文」的会话类型。

### 3.17 中栏标签页（已实现 · M25）

中栏原来一次只显示一个会话，切换必须回左栏长列表里找。排查「A 设备正常 B 设备异常」时要在两三个会话之间反复跳，而左栏可能正被筛选条件收窄着，每次都得重新定位。标签条把「手头正在跟进的几个会话」固化成一排入口。

- **两层状态而非一个**：`useStore.activeId` 回答「现在看哪个」，只能有一个；`useTabs.ids` 回答「手头在跟进哪几个」，是有序集合。标签只存会话 id，会话对象仍从 `useStore` 取——这样改名、状态灯、协议类型变化都会自动反映到标签上，不需要维护两份数据、也不会出现标签显示旧名字的问题。
- **预览标签解决标签爆炸**：借用编辑器的做法。左栏单击进来的会话落在同一个「预览槽位」里反复替换（标签名显示为斜体），只有明确表达了「要留着它」才提升为常驻：`Ctrl+单击` 左栏、双击左栏项、双击标签本身，或者**在该会话里真的发过报文**。最后一条挂在 `useStore.send` 里而不是发送按钮的点击处理里，因为 MQTT 发布、Modbus 写寄存器、报文片段都走这同一个出口，逐个补容易漏。
- **兜底开标签而非逐点补**：切换会话的入口有五处（左栏、命令面板、看板流量排行、搜索结果回跳、`Ctrl+Tab`），所以「确保焦点会话有标签」统一挂在 `activeId` 的副作用里，新增入口不必记得补这一步。
- **手势沿用既有肌肉记忆**，不自创：单击切换、中键关闭、双击钉住、拖拽排序、右键出菜单（固定 / 关闭 / 关闭其他 / 关闭右侧 / 全部关闭）、`Ctrl+W` 关当前、`Ctrl+Tab` 循环。`Ctrl+W` 必须 `preventDefault`，否则 Electron 默认行为是关掉整个窗口。
- **`Ctrl+Tab` 只在标签间循环**（有两个以上标签时），没有标签才退回全部会话。装了三十个会话的工作区里逐个 Tab 过去毫无意义，浏览器的 `Ctrl+Tab` 也只走已打开的标签。另外循环切换时**不会**把预览标签钉住，否则转一圈标签就全变常驻了。
- **溢出处理**：标签条只有 34px 高，横向滚动条会吃掉三分之一，所以隐藏滚动条，改为把滚轮的 `deltaY` 转译成 `scrollLeft`（不转译则滚轮在标签上毫无反应），并让激活标签在切换时 `scrollIntoView`——否则 `Ctrl+Tab` 切到屏幕外的标签看起来像什么都没发生。
- **持久化的一个坑**：标签列表落 `localStorage`，同时需要「会话被删则清理死标签」。但会话列表是异步 IPC 拉回来的，首帧是空数组，此时清理会把刚恢复的标签全判成已删除——表现为重启后标签只剩当前一个。所以 `useStore` 新增了 `sessionsLoaded` 标志（不能复用 `initialized`，后者在 `init()` 里同步置真，只用于防重复订阅），清理逻辑必须等它。
- **侧栏折叠按钮收进标签条左端**：原来是浮在报文区左上角的绝对定位按钮，会盖住时间轴第一行。看板与历史页是整页系统视图，标签列表置空但折叠按钮保留——否则在看板里把侧栏收起来就再也展不开了。

### 3.18 搜索结果回跳原会话上下文（已实现 · M24）

全局搜索原来只有一个落点：`Enter` 跳历史页用同一关键字续查。问题是历史页的结果**全是命中行**，命中行之间那些没命中关键字的报文（握手、心跳、错误响应）恰恰是判断因果最需要的，反而看不到。所以补了第二个落点。

- **两种手势并存**：`Enter` 保持跳历史页续查；`Shift+Enter`（或结果行右侧的「前后文」小按钮）打开「历史上下文」浮层。老习惯不被打断，新能力挂在同一个手势附近。
- **锚点用 `(ts, id)` 双字段而不是 offset**：分页查询要定位一行得先算出它在结果集里的第几条，而这个序号会随后续写入不断漂移，翻页时会看到错位。上下文查询直接以命中行的 `(ts, id)` 为界，向更早方向 `ORDER BY ts DESC, id DESC` 取一批再反转、向更新方向 `ORDER BY ts ASC, id ASC` 取一批，两次查询都能吃到 `idx_frames_session_ts` 索引，也不受并发写入影响。
- **边界靠 `LIMIT n+1` 探测**：多取一条就知道该方向还有没有更多，不用额外发 COUNT。到头时界面显示「—— 这是该会话在历史库中最早/最新的记录 ——」，中间则显示「↑ 再往前 50 条 / ↓ 再往后 50 条」，单向上限 500 条。
- **浮层而非整页**，`zIndex: 96` 压在搜索面板（90）之上。`Esc` 用 window 捕获阶段监听并 `stopPropagation`：浮层只有 `tabIndex=-1` 没夺焦点（焦点还在搜索框里），挂在面板节点上的 `onKeyDown` 根本收不到事件；捕获阶段拦下来还能保证 `Esc` 只关最上层这一层，不会连带把底下的搜索面板一起关掉。
- **命中行三通道标记**：`--selected-strong-bg` 底色 + 左侧 `--text-0` 色条 + 加重字色，另在行内右侧挂一枚「命中」小标签。首次加载后 `scrollIntoView({ block: "center" })` 居中一次（用 ref 加锁，否则点「再往前」加载会被反复拽回锚点），顶部「回到命中」按钮可手动复位。
- **格式与跳转**：frame 类支持 TEXT / HEX / B64 三种视图切换，关键字在正文里高亮（上限 60 段，避免一条报文命中上百次时切出过多节点）。原会话仍在则顶部出现「打开实时会话」，一键切回实时时间轴；会话已删除时退化为只读上下文（历史行冗余了会话快照字段）。
- **锚点已被清理时的降级**：保留策略可能已经把那一行删了，此时返回 `focusIndex: -1` 并提示「这条记录已被历史保留策略清理」，不做静默空白。

### 3.19 Mock 录制转路由（已实现 · M28）

**这是 Mock 工具最省人力的一个功能**：把「手写路由」变成「录一遍」。

- Mock 会话开启代理透传并指定上游地址后，未命中路由的请求转发到真实后端，请求与响应一并留档。
- 「录制转路由」面板把请求日志聚合成路由草稿：自动填好方法、路径模式、状态码、响应头与响应体，路径里的数字段 / UUID / 长 hex 段推断成 `:param`。
- 参数名取「前一段的单数 + Id」，`/api/users/1001/orders/77` 推断为 `/api/users/:userId/orders/:orderId`，而不是一串无意义的 `:id1 :id2`。
- 同方法同模式的请求合并成一条，示例响应取最后一次成功响应；多次响应体不一致时标「响应不一致」提醒改用脚本模式。
- 三个开关控制录什么：只转未命中路由的请求、忽略 4xx/5xx、已有同路径「跳过 / 覆盖」。
- 可勾选「同时存为场景」，生成的响应同时写进一个带时间戳的快照场景（如「真实快照 08-29 16:20」）并立即激活，得到「真实后端快照」与「异常注入」的对照组。

**实现要点（为什么这样做）**

| 决策 | 原因 |
|------|------|
| 优先级按「路径具体程度」自动算（固定段 ×10 − 参数段 ×3） | Mock 引擎按 priority 从大到小匹配。若按出现频次排，`/api/list` 这类宽路径会挡住 `/api/list/:id`，匹配就错了；用具体程度排序，用户完全不用手调数字 |
| 日志响应体上限从 4 KB 提到 256 KB | 截断过的 JSON 转成路由就是一段坏报文，前端拿到直接解析失败。录制场景下「存得下完整响应」比「省内存」重要得多 |
| 代理透传落日志前先按 `content-encoding` 解 gzip / deflate / br | 上游普遍开压缩，不解压存下来的是二进制乱码，草稿的响应体没法用。转发给客户端的字节仍是原样，不影响透传行为 |
| 代理转发时把 Host 头改成上游 host | 原先转发的是 Mock 自己的 host，按域名分流的上游（网关 / 多租户）会一律 404，录不到任何有效响应 |
| 丢掉 content-length、逐hop 头、CORS 头、content-encoding | 响应体后续会被编辑，长度对不上浏览器直接判报文损坏；逐hop 头是那一次 TCP 连接的属性；CORS 由 Mock 自己统一加 |
| 用「排除集」而非「选中集」记勾选 | 默认全选，用户通常只想剔掉少数几条，反选交互更省点击 |
| 「跳过」模式下已存在的路由仍计入场景快照 | 否则「保留现有路由 + 只想看真实响应」这个组合无法表达 |

### 3.20 接口集合定时巡检（已实现 · M28.2）

把接口测试里已保存的集合按周期自动跑一遍，断言失败就发系统通知。定位是**联调阶段的轻量可用性监控**，不追求替代专业监控系统——价值在于挂机时不用一直手点「发送」。

- 任务配置：名称、周期（10 秒 / 30 秒 / 1 / 5 / 15 / 30 分钟 / 1 / 6 小时）、环境（可跟随当前环境或锁定某个环境）、步骤间隔、失败即停止、启用开关。
- 巡检范围：不勾选任何请求 = 集合全部，之后往集合里新增的接口自动纳入；也可只勾选其中几个。
- 通知策略三档：仅失败时通知 / 每次都通知 / 不通知。失败通知支持「连续失败 N 次才通知」。
- 巡检历史留档：每次运行记录时间、通过数、断言数、总耗时，失败时直接在行内显示「哪个接口 → 哪条断言没过」，hover 可看全部失败项。
- 未读失败数以红点形式出现在左栏「接口巡检」图标与「工具」菜单项上，打开面板即视为已读。
- 任务与历史随 localStorage 落盘（`toolbox.monitor.v1`），历史上限 200 条。

**实现要点（为什么这样做）**

| 决策 | 原因 |
|------|------|
| 执行逻辑抽成 `runCollection.ts`，手动「批量运行」与巡检共用 | 各写一份必然出现「手动跑过了、巡检报失败」这种最难排查的分歧：变量替换顺序、断言判定、失败即停语义都是细节密集的地方 |
| 调度器 `useMonitorScheduler` 挂在应用外壳，不挂在接口测试面板 | 巡检的全部意义就是「界面关着也在跑」。绑在面板上，一关面板监控即停，等于没做 |
| 每 5 秒醒一次自己判断谁到期，而不是给每个任务 `setInterval` | `setInterval` 在窗口被系统节流时会漂移，长间隔任务能漂出好几分钟；按 `lastRunAt` 比对当前时间，无论节流多久醒来都能算准。周期改动也不需要重建定时器 |
| 任务串行执行，用 `useRef` 而非 store 里的 `runningId` 做互斥 | 调度是异步的，靠 store 值会因闭包拿到旧值而重复启动同一任务；串行也避免多任务同时发请求把本机端口和上游打满 |
| 恢复时保留 `lastRunAt` | 否则每次重启应用，所有任务都会齐刷刷立刻跑一轮 |
| 通知加「连续失败阈值」 | 真实网络偶发一次超时太常见，每次都弹通知会让人很快把系统通知整个关掉，功能就废了 |
| 周期下拉把当前值兜进选项列表 | 预设档位覆盖不到的秒数（导入配置 / 手改存储）若不补进列表，自绘下拉会退回 placeholder，看起来像「没设周期」，实际任务正常在跑——这种不一致最容易误判 |
| 右栏改成设置区固定 + 历史区独立滚动 | 历史会长到几百条，整栏滚动会把「任务设置」顶出视野，改个周期得先滚回顶部 |
| 系统通知点击后把窗口提到前台 | 点了没反应会让人以为通知是坏的 |

### 3.20.1 报文断言告警与告警中心（已实现 · M28.3）

接口测试早就有断言，收发报文一侧原本没有——设备半夜把温度飙到 90 ℃、状态字翻成非零，只能靠人盯着时间轴。这一节把断言补给报文侧。

- **判定对象三种**：
  - *解析字段*：复用协议解析模板把报文拆成字段，对某字段做数值判定（大于 / 小于 / 等于 / 不等于 / 落在区间 / 超出区间）。字段带单位时提示里自动带上，例如 `温度 82.4 ℃ > 80 ℃`。
  - *报文文本*：按 UTF-8 解码后做包含 / 不包含 / 正则 / 等于 / 不等于。
  - *校验结果*：模板配了 sum8 / xor8 / CRC16 时，校验不符即命中。
- **作用范围**：全部支持告警的会话 / 按连接类型 / 指定某个会话。
- **方向**：接收 / 发送 / 不限。**级别**：警告、错误。
- **冷却**：不冷却 / 10 秒 / 30 秒 / 1 分钟 / 5 分钟。
- **命中动作**：高亮报文行（左侧色条 + 淡染底 + 行尾说明徽标）、系统通知、自动断开会话。
- **告警中心**：*告警记录*页把报文告警与巡检失败按时间倒排在同一条时间线（时间 / 类型 / 级别 / 规则或接口名 / 来源 / 说明 / 报文快照 HEX），可导出 CSV；*报文规则*页管理规则并显示每条规则的累计命中次数。左栏图标与「工具」菜单在有未读时出红点，打开即已读。
- 规则与事件落 localStorage（`toolbox.alertRules.v1` / `toolbox.alertEvents.v1`），事件上限 300 条。

**实现要点（为什么这样做）**

| 决策 | 原因 |
|------|------|
| 判定接在 store 的收帧回调里、入队之前 | 此刻这一帧刚从 IPC 反序列化出来，还没有任何持有者，可以就地打标记；等它进了 React 状态再回头改，就得复制整条报文数组并触发一次额外渲染 |
| 规则表为空时判定函数第一行即返回 | 这段代码在高吞吐下每秒被调用上千次。绝大多数用户绝大多数时间没配告警，这条路径必须等于零成本——连字节解码都不能做 |
| 文本判定自己按 UTF-8 解码，不复用 `Frame.text` | TCP / 串口适配器入帧时 `encoding` 是 `hex`，`Frame.text` 里躺的是 `53544154…` 这样的十六进制串。拿它匹配「包含 ALARM」永远不会命中，而用户看到的 TEXT 视图明明有 ALARM——这类不一致最难自查 |
| 冷却台账独立成 `cooldown.ts` 的模块级 Map | 一是打断 `useAlerts` 与 `alertRuntime` 的循环引用（store 要清冷却、运行时要写冷却）；二是 store 的每次写入都连带 localStorage 持久化，放在热路径上等于每帧写盘一次 |
| 冷却在「命中之后」判断，不在之前 | 先判定再看冷却，规则的命中次数才是真实的。否则统计会随冷却设置漂移，用户没法用它确认「规则到底在不在生效」 |
| 改完规则清掉该规则的冷却 | 不清会出现最容易被当成 bug 的现象：把阈值从 80 调到 20，报文明显超标却不报警，实际是上次命中的冷却还没过 |
| 命中统计与事件落档批量提交（200ms） | 一条异常报文往往连着来几百条，逐条 setState 会把界面淹掉 |
| 高亮只留第一条命中规则，error 优先 warn | 一行同时触发多条规则时把它们都堆到行尾，会把报文内容挤出可视区。全部命中在告警中心里能看到 |
| 行高亮用 `boxShadow: inset 2px` 而不是 `borderLeft` | 虚拟列表按固定行高估算滚动位置，真实边框会让每行宽出 2px 并触发重排 |
| 报文快照 HEX 截断到 64 字节 | 全量存会让 localStorage 迅速膨胀，而写入发生在收帧路径上，直接影响高吞吐时的流畅度；64 字节足够对照定位 |
| 能力矩阵新增 `alertRule` 开关，HTTP Mock 置 false | Mock 没有报文字节，挂在它上面的规则永远不会命中；把「哪些模块支持告警」写进矩阵，而不是在界面里再补一个 `kind === xxx` 判断 |
| 规则数据在应用外壳启动时就 `load()` | 判定挂在收帧路径上，而规则原本只在告警中心挂载时加载。不提前恢复，重启后第一次收帧会因为规则表是空的而静默跳过 |

### 3.22 工程化与可观测（规划 · M31）

- **性能剖析面板**：记录渲染帧耗时分布、IPC 往返延迟、SQLite 写入队列积压、内存缓冲占用。报文缓冲上限已到 5 万条，出现卡顿时需要能自证是哪一层的问题，而不是靠猜。
- **应用自动更新**：`electron-updater` + 静态文件服务器（或对象存储），启动时静默检查、后台下载、下次启动生效，配「跳过此版本」。省掉每次手动发安装包。
- **工作区 Git 化**：允许把工作区目录指向一个 git 仓库路径，会话配置、协议模板、接口集合都以文本形式落盘（分文件而非单个大 JSON），团队通过 git 共享与评审配置变更。
- **检查器折叠状态记忆**：右栏各分组的展开 / 折叠状态按会话类型持久化，不用每次重新展开。

### 3.23 分屏与报文对比（已实现 · M27）

- **分屏对比**：标签拖到中栏右半边、或标签右键「在右侧打开」、或视图菜单 `Ctrl+\` 形成左右分屏，两个会话的报文时间轴并排。排查「A 设备正常 B 设备不正常」时不用来回切。分隔条可拖动（比例夹在 0.2–0.8，双击回中），标签右键还可「左右互换」。
- **报文级 diff**：进入「对比」挑选模式后报文行首出现选择位，勾选两条（同会话或跨会话）自动打开对比视图。字节级对齐高亮差异位，HEX 与解析后字段表两种视角都支持。
- **时间轴联动**：分屏时勾选「时间轴联动」，一侧滚动另一侧按时间戳跟随到同一时刻，用于对比上下游报文时序。

**实现要点（为什么这样做）**

- **对齐算法用 LCS 而不是逐位置比**：报文最常见的差异是「中间多了一个字节」，逐位置比会把插入点之后的全部字节标成不同，噪声压过信号。LCS 序列对齐能识别插入 / 删除，回溯后再把相邻的「仅左 + 仅右」合并成「替换」——「A 变成 B」比「删 A 再插 B」更贴近人的理解。DP 表用一维 `Int32Array`，超过 150 万格预算时退化为逐位置比并在头部挂「逐位置比较」提示，避免长报文把渲染线程卡死。
- **对比面板上下排布而不是左右分栏**：一行 16 字节已经占掉不少横向空间，左右分栏会让每侧只剩 8 字节一行，偏移量对不上直觉。上下排布保持两侧偏移完全对齐，视线上下扫就能看出哪一位变了。
- **差异着色只用明度与字重**：延续全局「无彩色强调色」约束。差异格用加深底色 + 提亮字色 + 加粗三通道同时表达，仅一侧存在的字节额外加下划线——只靠底色在浅色主题下几乎看不出来。
- **挑选用显式模式而非 Ctrl+单击**：报文行本身已有点击行为（展开字段表、按主题过滤），叠加隐式手势会互相打断。挑满两条后继续点会替换较早那条，支持「固定一个基准依次比后面几条」。
- **分屏状态用单字段 `splitId` 而不是「标签数组 + 分界下标」**：分屏是临时的对比动作而非常态布局，退出分屏就是置 null，不需要维护两组标签顺序，也不会在关标签时产生「分界线该往哪挪」的歧义。
- **焦点侧概念**：分屏后「当前会话」有两个候选。菜单与快捷键统一走 `focusPane`，否则会出现「在右半区点了断开，结果左边那个断了」这类最难排查的错觉。
- **时间轴联动单独开 store 且不持久化**：联动是每次滚动都在变的高频状态，而布局 store 每次变更都写 localStorage，混在一起会让滚动变成磁盘写。跟随侧靠自增 token 判断「这是一次新滚动」而不是比较时间戳——两侧时间戳可能恰好相同。
- **分屏时两侧收窄 UI**：检查器固定 280px，半宽栏里再切掉它连一行 HEX 都排不下；类型徽标、字节统计、协议模板、录制回放导出等低频项在分屏时收起，退出即恢复。这不是功能删减，而是让半宽栏的工具条不至于堆成三四行把报文区挤没。

### 3.24 模块功能边界与输入区可拉伸（已实现 · M28.1）

前几个里程碑一直在往会话界面加功能，但加的时候没有区分「这个功能属于哪些协议」，
结果是所有连接类型共用同一套工具条与发送区。三个具体后果：

- WebSocket 会话上挂着「追加 CRLF」，可 WS 自带消息边界，追加结束符只会污染载荷；
- Modbus 会话能把发送编码切成 TEXT，而 Modbus 是纯二进制帧，切过去发出去必然是废帧；
- 协议解析模板不分归属，串口会话的解析下拉里躺着「Modbus 读保持寄存器」，选中后字段名（从站地址、起始地址）跟真实报文毫无关系。

**能力矩阵（`app/meta.ts` 的 `KIND_CAPS`）**：把「模块有哪些功能」抽成数据，界面按矩阵渲染，
而不是继续堆 `kind === xxx` 的条件分支。新增协议时只补一行，不必去十几处逐个打补丁。

| 能力 | TCP 客户端/服务端 | WebSocket 客户端/服务端 | 串口 | MQTT | Modbus TCP/RTU | HTTP Mock |
|------|------------------|------------------------|------|------|----------------|-----------|
| 协议解析模板 | ✅ | ✅ | ✅ | ✅ | ✅ | — |
| 结束符（CR/LF/CRLF） | ✅ | — | ✅ | — | — | — |
| 发送编码可切换 | ✅ | ✅ | ✅ | ✅ | — (HEX 固定) | — |
| 报文规则应答 | ✅ | ✅ | ✅ | — | — | — |
| 录制与回放 | ✅ | ✅ | ✅ | ✅ | ✅ | — |
| 循环发送 | ✅ | ✅ | ✅ | ✅ | ✅ | — |
| 发送目标选择 | 仅服务端 | 仅服务端 | — | — | — | — |
| 发布主题 | — | — | — | ✅ | — | — |
| 点表轮询 | — | — | — | — | ✅ | — |
| 订阅管理 | — | — | — | ✅ | — | — |

**模板归属**：`ProtoTemplate` 新增 `kinds?: ConnectionKind[]`。空数组 = 通用模板；
内置的 Modbus 示例标为仅 `modbus-tcp` / `modbus-rtu`。模板面板新增「适用模块」多选与
「本模块 / 全部模板」两档过滤，新建模板默认继承打开它的那个会话的类型。
旧数据没有该字段一律视为通用，升级后不会突然空掉。

**输入区可拉伸**：发送区顶部新增拖拽分隔条，高度写进布局状态并落盘，跨会话与重启都记得。
WebSocket 自定义 Header、Mock 响应模板与脚本、接口测试请求体、工具箱输入统一改用
`ResizableTextarea`（自绘拖拽把手 + 受控高度）。

**实现要点（为什么这样做）**

- **原生 `resize: vertical` 在本项目里必然失效**：这些 textarea 都是 flex 列容器的直接子项，原生手柄写的是 inline `height`，而 flex 会在下一次布局按 `flex-shrink` 把它压回去 —— 手柄画得出来，拖了没反应。修法有两条：容器加 `flexShrink: 0`，以及把高度提升为受控状态。两条一起做才稳，只做前者仍会被父级 `maxHeight` 截断（接口测试的请求体就撞过这个，`tabBody` 的 `maxHeight: 220` 把拉高的部分直接切掉了）。
- **发送区拉的是整块而不是输入框**：发送区里还有编码开关、结束符、片段行。用户的意图是「把发送区拉大」，所以分隔条放在发送区上沿，输入框用 `flex: 1 1 0` 吃掉剩余空间。
- **高度存布局 store 而不是组件内 state**：切会话、切标签都会重挂组件，存组件里等于每次回到默认高度。存 store 顺带获得跨重启记忆。
- **不可用的功能直接不渲染，而不是禁用**：禁用态需要用户先点一下才知道不能用；直接不渲染再配合模块徽标（发送区左侧标出当前协议），「这个模块能做什么」一眼可见。唯一例外是 Modbus 的编码开关，它换成「HEX 固定」的说明标签 —— 这里需要解释「为什么不能切」，空着反而像功能缺失。
- **模板归属放在模板上而不是会话上**：一个模板可能同时适用于 TCP 与串口（同一套自定义帧走不同物理链路很常见）。写在会话上就得每个会话各配一遍。

### 3.25 后续模块功能推荐路线（规划）

到 M28.3 为止，「连上 → 收发 → 看懂 → 存档 → 自动化 → 出问题告警」这条主链路已经闭合。下面这份清单是按「投入产出比 × 现有缺口」排的推荐顺序，而不是按功能听起来的大小。判断依据有三条：**是否补上协议矩阵的明显空洞**、**是否能复用已有基础设施**、**是否解决当前只能靠人肉的环节**。

#### 第一梯队：缺口明显且成本低

| 推荐项 | 为什么推荐 | 复用什么 |
|--------|-----------|---------|
| ~~**UDP 客户端 / 服务端**~~（已于 M29 实现，见 3.26） | 这是协议矩阵里最刺眼的空洞。TCP、WebSocket、串口、MQTT、Modbus 都有了，唯独 UDP 没有——而工业采集、音视频信令、组播发现、syslog 全是 UDP。它是列表里唯一「用户一看就知道少了」的东西 | Node `dgram` 一个适配器；分帧、编码、告警、历史、看板全部现成。UDP 无连接，反而不需要重连逻辑 |
| **Modbus 从站模拟（Slave / Server）** | 现在只有主站。没有真实设备时无法自测，用户得先去找一个第三方模拟器才能验证自己的点表配得对不对——这跟「HTTP 有 Mock 服务」的缺失是同一类问题 | `modbus/pdu.ts` 的编解码是双向的，点表结构可直接当寄存器区；界面复用点表面板 |
| **报文标注与书签** | `FrameMeta.note` 字段早就在协议里留好了，但没有任何界面能写。抓到一条可疑报文时，现在只能靠记时间戳。加个右键「标注 / 加书签」+ 书签跳转，成本极小 | 字段已存在；跳转复用搜索上下文那套锚点 |
| ~~**HAR 导出**（3.21 的一部分）~~ **已实现 M29.1** | 团队协作里「把这个请求发给同事复现」目前只能截图。HAR 是 Chrome DevTools / Postman / Fiddler 都认的格式，一次实现三处受益 | 实测 `HttpLogEntry` 字段够用；接口测试历史需补响应摘要字段，历史库缺头部（导出时在 comment 里注明） |

#### 第二梯队：把工具接进团队流程

| 推荐项 | 为什么推荐 | 注意点 |
|--------|-----------|-------|
| **OpenAPI 导入 / 导出** | 读 OpenAPI 一键生成接口集合，是「让别人愿意用这个工具」的关键一步——否则每个接口都要手敲一遍 URL 和参数。反向把 Mock 路由导出成 OpenAPI 骨架，可以直接当前后端契约 | OpenAPI 的 schema 引用（`$ref`）与 oneOf 组合要做展开，这是主要工作量 |
| **Postman Collection v2.1 双向** | 存量团队资产大多在 Postman 里。能导入意味着零成本迁移，能导出意味着不锁死用户 | 变量语法 `{{var}}` 与本项目一致，映射较直接 |
| **命令行 / CI 模式** | 巡检解决了「本机挂机盯着」，但接口集合真正的价值是进流水线。提供 `--run-collection xxx.json --env prod` 的无界面模式，退出码反映断言结果，就能挂进 GitHub Actions | 需要把 `runCollection` 从渲染层抽到共享层（它目前只依赖 `window.toolbox.sendHttpTest`，抽离时改成注入式发送器即可） |
| **场景脚本编排** | 现在的自动化只有「循环发同一条」。真实联调是「发握手 → 等应答 → 校验字段 → 发指令 → 等 3 秒 → 断言」。做一个简单的步骤序列（发送 / 等待匹配 / 延时 / 断言 / 跳转），覆盖面远超循环发送 | 建议做成数据驱动的步骤表而不是自由脚本，可复用 Mock 的 `vm` 沙箱做条件表达式 |

#### 第三梯队：体验与工程化

| 推荐项 | 为什么推荐 |
|--------|-----------|
| **应用自动更新（electron-updater）** | 每加一个功能都要用户手动装一次安装包，这会直接压低新功能的到达率。做完这项之后所有后续迭代的分发成本归零，所以越早做越划算 |
| **性能剖析面板** | 报文缓冲上限已经到 5 万条，告警判定又挂在收帧路径上。将来出现卡顿时需要能自证是哪一层（渲染帧耗时 / IPC 往返 / SQLite 写入积压 / 告警判定），而不是靠猜 |
| **数据可视化增强** | 当前曲线只支持「标记字段随时间画折线」。可补：多字段双 Y 轴、告警阈值线画在曲线上（和 M28.3 天然配套）、时间窗口缩放与游标读数 |
| **会话分组与标签增强** | 分组现在是单层字符串。可补：拖拽改分组、分组批量启停、按标签一键启动一组会话（联调时往往要同时拉起五六个连接） |
| **工作区 Git 化** | 会话配置、协议模板、接口集合分文件落盘后可用 git 评审与共享。价值明确但受众窄于上面几项，故排后 |
| **多窗口** | 分屏已能满足绝大多数并排需求，多窗口主要是多显示器场景。收益相对有限，且会话状态跨窗口同步的复杂度不低 |

#### 明确不建议现在做

- **gRPC 调试**：需要引入 proto 解析与动态 stub，工作量接近再做一个 MQTT 模块，而受众远小于 UDP。等有明确需求再说。
- **内置 MQTT Broker**：本地起 broker 听起来对称（因为 HTTP 有 Mock），但公开的 mosquitto / EMQX 一键就能跑，自己实现收益低。
- **协议模板可视化拖拽编辑器**：现在的字段表已经能表达绝大多数帧结构，拖拽编辑器主要是观感提升，不解决新问题。

### 3.26 UDP 客户端 / 服务端（已实现 · M29）

协议矩阵里最后一个明显空洞。工业采集、组播发现、syslog、音视频信令大量走 UDP，之前只能借第三方工具。

- **客户端**：默认目标地址 + 端口；本地端口可固定（0 = 系统随机），满足「设备只回固定端口」的协议；可选定时心跳包维持 NAT 映射。
- **服务端**：绑定地址 + 端口收包；对端按来源 `ip:port` 派生；发送可广播全部已知对端或指定其一。
- **广播**：勾选后允许发往 `255.255.255.255` 与网段广播地址。
- **组播**：填组地址（如 `239.0.0.1`）在绑定后加入该组，TTL 默认 1；配合端口复用可与本机其他程序共用端口抓包。
- 协议解析模板、报文断言告警、录制回放、循环发送、数值曲线、历史落库与看板统计全部复用既有实现，未新增任何专用通路。

**实现要点（为什么这样做）**

| 决策 | 原因 |
|------|------|
| 不接 `FrameSplitter` | `dgram` 的一次 `message` 事件本身就是一个完整数据报，边界由协议保证。再套「按分隔符 / 按长度」拆一遍，是把正确的边界主动切碎——与 M28.1 认定「WebSocket 不该有结束符」属同一类边界错误 |
| 能力矩阵里 `terminator: false` | 同上，追加 CR/LF 只会污染载荷。写进矩阵而不是在界面里补 `kind === xxx` 判断 |
| 不接 `Backoff` 重连，`canReconnect` 不含 UDP | 没有连接就没有断线，重连退避在这里是纯空转。给出「自动重连」开关反而让人以为它在保障可达性 |
| 客户端状态仍用 `connected`，但启动日志写明含义 | 复用既有状态机比新增一个 `ready` 态划算（状态色、看板统计、筛选器都要跟着改）。代价是语义模糊，所以在连接日志里明确写「UDP 无连接，此状态仅表示可收发」 |
| 对端按 `ip:port` 即时派生，靠空闲超时淘汰 | UDP 没有 `close` 事件，等不到「断开」。不淘汰的话，一次端口扫描带来的成百上千个临时源端口会把对端列表撑爆。默认 60 秒，可配，0 = 不淘汰 |
| 淘汰扫描周期取 `min(idle, 15s)` 且不低于 2 秒 | 周期等于淘汰时长会让实际淘汰延迟翻倍；太密则在空闲时白烧 CPU |
| `kickPeer` 只从列表移除，并在日志里说明 | 协议上没有任何办法阻止对方继续发包。沿用「踢出」按钮但把真实语义写进系统日志，比藏起按钮更诚实 |
| 服务端默认开启 `reuseAddr`，客户端默认关闭 | 服务端的典型场景是组播抓包与多进程共存；客户端绑随机端口，复用没有意义反而掩盖端口冲突 |
| 建会话时不写 `config.framing` | 写个 `none` 会让检查器多出一行「分帧 none」，在 UDP 上是无意义参数。检查器也显式跳过 UDP 的分帧行，兼容旧配置残留 |
| `SessionConfig` 单列 `udpBindHost/udpBindPort`，不复用 `host/port` | 客户端同时需要「目标地址」与「本地绑定端口」，两者若挤在 `host/port` 上必然语义打架 |
| `SessionView` 的 `isServer` 改读能力矩阵 `caps.peerTarget` | 原来是 `kind === tcp-server \|\| kind === ws-server` 的硬判断，每加一种服务端都要来补一次。这类「加协议时容易漏改」的散点是模块边界失控的起点 |
| `Inspector` 的可编辑字段从嵌套三元改成查表 | 原写法每加一种连接类型就多一层缩进，漏写分支会静默落到空数组（表现为「改参数」按钮点了没内容）。查表后新协议加一行即可 |

### 3.27 TLS 证书管理（已实现 · M29.2）

HTTP Mock 早就有「启用 HTTPS」开关，但配套的证书入口一直不存在：新建对话框里写着「需在设置中提供证书」，而那个设置页从未实现。结果是勾了必定起不来，且报错来自 Node 底层（`ERR_OSSL_PEM_NO_START_LINE`），用户无从判断问题在哪。这是文档承诺与实现不一致里最伤信任的一类，故插在 M29.1 之前先补。

- **自动兜底**：新建 HTTP Mock 会话时若勾了 HTTPS，创建流程直接生成一张 `localhost` + `127.0.0.1` 的自签证书写入会话配置，开箱即用。
- **证书面板**（工具栏「证书」）：生成自签 / 导入证书文件 / 粘贴 PEM 三条路径，外加当前证书体检卡（主题、签发者、有效期与剩余天数、SAN、私钥匹配、指纹、落盘路径）、导出证书、打开数据目录、清除证书、启用 HTTPS 开关。
- **启动前体检**：`http-mock` 适配器在 `createServer` 之前先校验证书与私钥，不通过就给中文原因并置 `error`，剩余有效期不足 14 天在系统日志里告警。
- **缺失可见**：启用 HTTPS 且证书为空时，工具栏按钮变为红色「证书缺失」。

**实现要点（为什么这样做）**

| 决策 | 原因 |
|------|------|
| 手写 ASN.1/DER 生成证书，不引入 `node-forge` / `selfsigned` | 密钥生成与签名 `node:crypto` 本来就有，缺的只是证书结构的编码。为此拖进数百 KB 依赖（且 `node-forge` 自带一套 JS 大数运算）不划算。代价是要自己保证 DER 正确，因此生成后立刻用 `new crypto.X509Certificate()` 回读校验 |
| 自签证书写成 CA（`basicConstraints cA=TRUE` + `keyUsage` 含 `keyCertSign`） | 不带 CA 标记的证书即使导入系统信任库，Chrome 仍报 `ERR_CERT_AUTHORITY_INVALID`。而「导入信任库消除警告」正是用户唯一能自救的路径，必须让它真的有效 |
| SAN 区分 `iPAddress` 与 `dNSName` 两种 tag | 把 `127.0.0.1` 写成 DNS 名，现代浏览器与 Node 的 `checkServerIdentity` 都不认。IPv4 走 `[7]`（4 字节原始地址），域名走 `[2]` |
| `notBefore` 回拨 1 小时 | 生成后立刻使用时，客户端时钟稍慢就会判成「尚未生效」。这类失败极难归因 |
| 有效期默认 825 天而非 10 年 | Chrome / Safari 对服务器证书接受的上限档位是 825 天，填更长会被直接判无效——「填得越久越省事」在这里是反直觉的坑，所以在界面里写明 |
| 导入证书用两次文件对话框，不做多选 | 多选返回的数组无序，靠扩展名猜哪个是私钥在 `.pem` / `.pem` 场景必然猜错，而猜错的表现是握手失败（难查）。两步选择多点一次，换来确定性 |
| 粘贴 PEM 校验不通过则「应用」禁用 | 允许存下一个必定起不来的配置，等于把错误从「现在可见」推迟到「启动时才炸」 |
| 证书落在 `userData/certs`，私钥 `0600` | 放安装目录会被升级覆盖，且 Program Files 无写权限。私钥收权限是最低成本的防护 |
| 启动前体检而非依赖 `createServer` 抛错 | 底层错误信息（`ERR_OSSL_PEM_NO_START_LINE`）不能指导用户行动。前置体检可以直接说「私钥与证书不匹配」并指向证书面板 |

### 3.28 Modbus 从站模拟（已实现 · M29.1）

**需求背景**：M22 的 Modbus 主站只能证明「请求发出去了」，证明不了「点表配得对」。字序、寄存器偏移、系数偏移这三类配置错了以后依然能读出数字，只是数字是错的 —— 缺的是一个真值由自己掌握的对端。手边没有 PLC 时，这个模块就充当那台设备。

**功能范围**

- **三种链路**：Modbus TCP 监听、RTU over TCP 监听、Modbus RTU 串口。数据区内核与链路解耦，换传输方式不用重填数据。
- **数据区表**：名称 / 区（4x 保持、3x 输入、0x 线圈、1x 离散输入）/ 起始 / 数量 / 初值 / 只读 / 自动变化（不变化 · 递增斜坡 · 正弦波 · 随机 · 翻转）/ 周期 / 上下限 / 步进。
- **实时值页**：每区按 10 列网格铺开，位区点击翻转、寄存器区就地改值，主站写入即时回显。
- **故障注入**：应答延迟、丢包率、强制异常码（0x01/0x02/0x03/0x04/0x06）。
- **支持的功能码**：01/02/03/04 读，05/06 单写，0F/10 多写。

**实现要点（为什么这样做）**

| 决策 | 原因 |
|------|------|
| 未声明的地址返回异常码 `0x02` 而不是乐观返回 0 | 这正是用从站自测点表的意义。越界给 0 的话，「地址填错一位」这个最高频的配置 bug 会被完美掩盖 —— 界面上照样有读数，且看不出异常 |
| 数据区内核（`modbus/slave.ts`）做成纯函数：请求进、响应出 | 不碰 socket 与串口，三种链路共用同一份实现，且可以脱离网络单独验证编解码 |
| 延迟与丢包放在适配器层，不进内核 | 它们是链路特性而非数据语义。混进内核后，内核那层就没法在无 I/O 的前提下自测 |
| 从站地址不匹配时**静默丢弃**（`pdu: null`），不回异常码 | 真实 RTU 总线上多台从站共享一根线，对不是自己的请求回包会污染其他从站的应答，把一个配置问题变成一个诡异的总线问题 |
| 数据区用 `Map<number, number>` 而非定长数组 | 「地址是否存在」本身就是要表达的语义，稀疏结构天然承载；同时避免用户填个起始 60000 就分配一大片内存 |
| `rebuild()` 保留已有地址的当前值 | 改个区名或加一行不该把主站已经写进去的数据清零，否则调试中途碰一下配置就得重来 |
| 监听失败**不接**指数退避重连 | 监听失败的原因基本只有端口被占用或权限不足，退避重试只是把一个应立即暴露的配置错误变成「一直连不上」。同时对 EADDRINUSE 直接提示 502 是特权端口、建议改 5020 |
| 动画由单一 `tick(now)` 节拍驱动（200ms），界面推送再合并到 120ms | 每个数据区各起定时器会在几十个区时把主进程压满；界面也不需要比人眼更快的刷新率 |
| TCP 每条连接维护独立接收缓冲 | 多主站并发时共用缓冲必然串包，而串包的表现是「偶发解析失败」，极难归因 |
| MBAP 长度域异常时提示「主站可能用的是 RTU over TCP」 | 这是该场景下最常见的真实原因，比报一个字节数不符更能直接指向解决办法 |
| 能力矩阵新增 `regionTable`，不复用 `pointTable` | 主站点表是「我要读哪些地址」，从站数据区是「我这有哪些地址、初值多少、怎么变化」。列、校验与写入语义都不同，合成一项必然在界面里长出一堆 kind 判断 |
| 发送框改成手动置值快捷入口（`holding 5 1234`） | 从站不主动发报文，但留一个点了没反应的发送按钮不诚实，索性给它一个真实用途 |
| 新建会话时预置 4 个示例数据区 | 空配置意味着任何地址都非法，用户第一次连上必然收到一片异常码，会以为模块坏了 |
| 实时值单区超 200 地址只渲染前 200 格 | 声明一万个地址是合理配置，画一万个格子不是 |
| 检查器的可编辑字段留空（端口只在从站面板里改） | 端口存在 `modbusSlave.port`，顶层再镜像一份必然出现两处不一致 |

**IPC 契约**：新增 `modbus:slave:updateRegions`（改数据区，即时生效不断连）、`modbus:slave:write`（界面就地置值）、`modbus:slave:snapshot`（拉全量当前值）；`SessionEvent` 新增 `modbusSlaveValues` 用于增量推送变化的区。

**验证方式**：裸 socket 扮演主站直验协议（读 0x03 正常、写 0x06 回显、读回一致、越界回 0x02、错功能码回 0x01、错 Unit ID 无应答、输入寄存器正弦波在动），再用本项目的 Modbus 主站会话与从站会话闭环（主站写 42 → 从站快照第 5 号保持寄存器为 42）。

### 3.29 报文标注与书签（已实现 · M29.1）

**需求背景**：报文以每秒几十条的速度刷动时，人的注意力是稀缺资源。看到可疑的一条，去查一次文档或跑一次对照用例，回来时它已经滚出屏幕；清屏或重启之后更是彻底没了。`FrameMeta.note` 字段在早期就预留好了，但一直没有界面入口，等于没有。这个模块把「钉住一条报文并写下判断」做成一步操作。

**功能范围**

- 报文行首星标：hover 显现、左键切换、右键直接标注并打开面板；数据行与系统事件行都支持
- 会话工具栏「标注 (N)」按钮、顶部「工具」菜单项、命令面板命令、`Ctrl+M` 全局快捷键四个入口
- 书签面板：会话下拉（只列有书签的会话）、关键字搜索（同时匹配标注 / HEX / 文本）、逐条标注编辑、跳回会话、导出 Markdown、按会话清除与全部清除
- 上限 500 条，单条 HEX 快照截断 128 字节，存 localStorage `toolbox.frameMarks.v1`

**实现要点（为什么这样做）**

| 决策 | 原因 |
|------|------|
| 书签存**自洽快照**（方向 / 时间 / 字节数 / HEX / 文本 / 会话名 / 类型），不只存 `frameId` | 报文缓冲是内存态。只存 ID 的话，清屏或重启后书签列表会变成一排点不开的空行 —— 而恰恰是「重启前看到的那条」最需要留住 |
| 定位请求做成 store 里的信号（`LocateRequest { sessionId, frameId, token }`），不用回调层层下传 | 书签面板既可能从顶部菜单打开（与任何 `SessionView` 没有父子关系），也可能从会话工具栏打开。用回调就得为前一种情况造一条穿透整个外壳的传参链 |
| `token` 单调递增而非用布尔标志 | 连续点同一条书签的「跳回会话」要能再次触发滚动；布尔标志第二次点时值没变，`useEffect` 不会重跑 |
| 未标注的星用 `opacity` 显隐，不按 hover 条件渲染 | 按 hover 插入 / 移除 DOM 会让整行宽度发生变化，报文快速刷动时整片列表横向抖动，非常晃眼 |
| 定位优先级：书签定位 > 分屏时间轴联动（`scrollTo={locateTarget ?? syncTarget}`） | 两者都想控制滚动位置，用户刚刚点下的「跳回会话」显然应该赢，否则表现为「点了没反应」 |
| 上限 500 条 + HEX 截断 128 字节 | 书签是人工挑出的线索，不是第二套历史库（全量落盘由 §3.13 的 SQLite 负责）。无限容量只会撑爆 localStorage 并拖慢启动 |
| 导出 Markdown 而非 CSV | 书签的产物是贴进工单或聊天的排查记录，读者是人；CSV 是给表格软件算数的格式 |
| 标注输入用 `draftRef` 镜像 + `onBlur` 读 ref | 直接在 `onBlur` 里读闭包变量会拿到过期值，「输完最后一个字立刻点走」会丢掉这次修改 |
| `markedIds` 做成 `Set` 传给每行 | 每行各自 `marks.some(...)` 是 O(行数 × 书签数)，报文列表本来就是高频重渲染路径 |
| 目标报文已不在缓冲时给顶部提示条并指向 `Ctrl+H` | 静默失败会被理解成功能坏了。明确告诉用户「它还在历史库里」，把死路变成下一步 |
| 原会话已删除时「跳回会话」变灰而非隐藏整条书签 | 快照本身仍有价值（当初记下的判断还在），只是回不去了 |

**验证方式**：开发版 CDP 实测 —— 点星标后按钮变「标注 (1)」且 localStorage 快照含正确 HEX；面板内输入标注后失焦持久化；「跳回会话」自动切标签并关闭面板；清屏后再定位出现红色提示条。深浅两套主题分别截图核对星标与面板（深色无白边、浅色按钮底色协调）。

### 3.30 HAR 导出（已实现 · M29.1）

**需求背景**：接口问题的排查成本大头在沟通，不在技术。「我这边参数是这么传的」之后就是截图、复述、来回确认。HAR 1.2 是 Chrome DevTools、Postman、Fiddler、Charles 共同支持的交换格式 —— 导一份发过去，对方拖进浏览器就看到完整请求与响应，不需要先装本工具。

**功能范围**

| 入口 | 导出内容 | 头部完整性 |
|------|----------|-----------|
| 接口测试面板 · 历史区「导出 HAR」 | 最近 100 条请求，含响应头与响应体 | 完整，认证头已还原 |
| Mock 会话工具栏「导出 HAR」 | 当前过滤结果对应的请求日志 | 完整 |
| 报文历史 · HTTP 请求页「导出 HAR」 | 查询条件命中的请求（上限 5 万条） | headers 为空（见下） |

**实现要点（为什么这样做）**

| 决策 | 原因 |
|------|------|
| HAR 构建抽到 `shared/har.ts` 纯函数层 | 三个来源分处两个进程（前两个在渲染层，历史库在主进程）。各写一份映射，早晚出现「同一次请求从不同入口导出，字段长得不一样」这种最难解释的分歧 |
| 导 HAR 而非自定义 JSON | 自定义格式等于把协作成本转嫁给对方 —— 对方得先装本工具才能看 |
| `startedDateTime` 用本地时区 ISO（`+08:00`），不用 `toISOString()` | 后者是 UTC，导出的文件在 DevTools 里整体差 8 小时，和现场日志对时间时极易看错。HAR 规范本身也要求带时区偏移 |
| 耗时未知时写 `time: -1` 而非 `0` | `-1` 是 HAR 规范里的「未知」。写 0 会被 DevTools 画成零宽时间条，看起来像请求瞬间完成，比不显示更容易误判 |
| `timings` 三项之和严格等于 `time`，且全部记在 `wait` 上 | 和不等于 `time` 时 DevTools 会拒绝该条 entry。本工具只测到总时长，没有 DNS/连接/首字节分段，记在 `wait`（等服务端响应）也是实际语义 |
| 请求体同时写 `bodySize` 与 `postData` | `postData` 才是 DevTools「Payload」页读的字段。只填 `bodySize` 的话字节数对得上但载荷是空的，看起来像请求没带 body —— 而 body 恰恰是排查 POST 接口最先要看的 |
| 接口测试导出时**还原认证头** | Bearer / Basic / API Key 在本工具里是独立配置，不在 Header 表。不补 `Authorization`，对方重放必然一片 401，看起来像接口坏了。代价是 token 明文落盘，界面上有明确提示 |
| 变量在导出时展开（`{{baseUrl}}` → 真实地址） | 对方没有你的环境变量表 |
| Mock 侧导出 `visible` 而不是 `logs` | 过滤条件是用户刚刚表达的意图。导出时忽略它、把全部日志塞进去，等于让人回去手工删。按钮上显示将导出条数 |
| 请求体字节数用 `TextEncoder` 而非 `String.length` | 中文一个字符不是一个字节，用 length 会让 `bodySize` 偏小，对方按大小核对时对不上 |
| URL 一律补成绝对地址（历史库用 `http://localhost` 占位） | HAR 规范要求绝对 URL。给相对路径时 DevTools 拒绝的是**整份文件**，不是跳过某一条 |
| 历史库导出的 HAR **不含头部**，而不是补表存下来 | 历史库按十万行量级设计，每条多存两份头部 JSON 体积可观，而这部分多数时候不会被读。折中是导出时在每条 `comment` 里写明「历史库未保存头部」，并在界面提示里指向 Mock 会话入口 |
| HAR 文件**不写 UTF-8 BOM**（CSV 仍写） | Excel 不带 BOM 会把中文认成乱码，所以 CSV 必须写；而 JSON 带 BOM 会让 DevTools 与多数解析器在首字符处直接报错 |
| `entry.comment` 里带上来源、命中路由与 Mock 场景名 | 同一个路由在不同场景下返回完全不同，缺了场景名这份文件会让人对不上 |
| 接口测试历史新增响应摘要字段，响应体截断到 8 KB | 没有响应的 HAR 在 DevTools 里只是一行空请求。但历史留 100 条，全量响应体会撑爆 localStorage —— 超限是**整体写入失败**，表现为「集合莫名清空」，极难归因。截断逻辑放在 store 的 `pushHistory` 而非调用点，因为将来集合运行与巡检也会写这里 |

**IPC 契约变更**：`history:export` 增加第四个参数 `format: 'csv' | 'har'`（默认 `csv`）。`'har'` 只对 `kind: 'http'` 生效 —— 报文是裸字节流，套不进请求/响应模型，硬导出得到的是一份处处为空的文件。

**验证方式**：把三条映射链路分别用 esbuild 打包后在 Node 里直验产物 JSON —— 字段完整性（HAR 1.2 必填项逐个检查）、`timings` 求和等于 `time`、中文 query 解码、认证头还原（Bearer 与含中文的 Basic）、变量展开、默认 Content-Type 补齐、`postData` 生成、耗时未知落 `-1`、无 BOM。

### 3.31 内置使用文档（已实现 · M29.3）

**需求背景**：功能已经铺到十几个模块，但对使用者只有一份仓库里的 README —— 而 README 是写给开发与打包用的，混着构建命令与实现取舍。需要查手册的时刻恰恰是手头正卡着的时刻，此时跳出应用去翻文件会打断排查，现场调设备时甚至连外网都没有。因此文档必须在应用内、离线可用。

**功能范围**

| 项 | 说明 |
|----|------|
| 入口 | 帮助菜单第一项、`F1`、命令面板搜「文档 / 帮助 / 手册」 |
| 结构 | 左目录常驻 + 右正文，共 17 章：快速上手、界面导览、TCP/UDP、WebSocket、串口、MQTT、Modbus 主站、Modbus 从站、HTTP Mock、接口测试、报文分析、告警监控、历史与看板、工作区、快捷键、常见问题 |
| 全文搜索 | 面板内 `Ctrl+F` 聚焦搜索框；目录上标出每章命中数；正文关键字高亮；搜索后自动跳到第一个命中章节 |
| 翻页 | 正文底部「上一章 / 下一章」 |
| 导出 | 「导出 Markdown」导出整本 |
| 同步产物 | `npm run docs:guide` 生成 `docs/使用文档.md` |

**实现要点（为什么这样做）**

| 决策 | 原因 |
|------|------|
| 正文以结构化数据（`GuideBlock[]`）为唯一来源，而不是一段 Markdown 字符串 | 同一份内容要供两个消费方：界面面板需要按章分栏与「命中几处」这类结构信息，仓库文档需要标准 Markdown。以 Markdown 为源就得在界面侧解析一遍，用正则切段落取结构很快失真；反向由结构化数据拼 Markdown 是确定性操作 |
| `docs/使用文档.md` 由脚本生成，不手工维护 | 手动同步两份文档迟早会分叉，而「界面写的和仓库写的不一样」是最难发现的一类偏差。脚本走 esbuild 打包临时 ESM 再 import，跑完删除，不引入 ts-node、不在仓库留产物 |
| 做成应用内面板而不是打开外部浏览器 | 离线可用是硬需求（现场无外网）；跳出应用也会打断当前排查上下文 |
| 面板内 `Ctrl+F` 在捕获阶段拦下并阻止冒泡 | 文档开着时按 `Ctrl+F`，用户想搜的显然是文档，而不是全局报文搜索 |
| 搜索无命中的章节压暗而非隐藏 | 整本的目录结构本身是信息。抽掉一半会让人以为文档变短了，也失去了「原来还有这一章」的发现路径 |
| 关键字高亮用 DOM 节点拼接，不用 `dangerouslySetInnerHTML` | 正文含 `{{}}`、`<>` 等字符，走 innerHTML 会被当标签解析，且凭空多一条注入路径 |
| `F1` 判断放在修饰键判断之前 | 键盘处理里有一句 `if (!mod) return`，放在其后会被直接吞掉。`F1` 是桌面应用的帮助键，用户会下意识按 |
| 换章节时把正文滚回顶部 | 从长章切到短章若保留滚动位置，会停在一片空白上，看起来像内容没加载 |
| 导出整本而不是当前章 | 拿去存档或转发时，缺章的手册没有意义 |

**验证方式**：开发版 CDP 实测 —— 帮助菜单项文本序列为「使用文档 F1 / 快捷键一览 Ctrl+/ / 关于 / 开发者工具 F12 / 重启应用」；面板打开后目录 17 项齐全；搜「串口」得到命中分布 5 章 4 处、7 章 2 处、11 章 1 处、17 章 3 处并自动跳到第 5 章，正文出现 2 处高亮；`F1` 可直接开面板；命令面板搜「文档」命中「打开使用文档」。深浅两套主题分别截图核对（深色无白边、浅色表格与目录选中底色协调）。

### 3.32 应用自动更新（已实现 · M31，M33 收缩为单一口径）

**需求背景**：工具已迭代到十几个模块，每次改动都要靠「群里发安装包 + 挨个提醒重装」分发，迭代成本随使用人数线性增长，且没人知道同事手里跑的是哪一版。分发摩擦一旦高于修一个 bug 的成本，迭代就会停。

**M33 的收缩（重要）**：M31 曾把更新源做成运行时可配 —— 界面上能选渠道（GitHub 发布仓库 / 自建服务器）、填仓库名、选下载代理。M33 把这一整块**移除**，更新地址改由打包时的 `electron-builder.yml` `publish.url` 唯一决定。

| 收缩前 | 收缩后 |
|--------|--------|
| 界面有渠道单选、仓库名输入框、代理下拉（6 项）、自定义代理输入框、实际地址回显 | 界面只剩两个复选框 |
| `UpdateSettings` 六个字段（kind / feedUrl / githubRepo / githubProxy / autoCheck / autoDownload）| 两个字段（autoCheck / autoDownload）|
| `shared/protocol.ts` 导出 `UpdateChannelKind`、`normalizeGithubRepo()`、`resolveUpdateFeedUrl()` | 三者全部删除 |
| 主进程每次检查前 `setFeedURL()` | 不调用，地址由 electron-updater 自己从 `app-update.yml` 读 |

**为什么收缩**：可配置的出发点是「换服务器不用重新打包」，但代价是把一件发布方只需决定一次的事，摊给每一个使用者 —— 他要判断填哪种来源、仓库名怎么写、代理选哪个。而这三处任何一处写错，表现都是同一个 404，用户无从判断错在哪。发布地址属于发布方的基础设施决策，不属于使用者的配置项。后续统一走一个口径的更新服务，客户端只需知道「去那里看有没有新版本」。

**功能范围**

| 项 | 说明 |
|----|------|
| 入口 | 帮助菜单最后一组、命令面板搜「更新 / update / 升级」 |
| 更新地址 | 打包时写入，运行时不可改。取自安装包内 `app-update.yml`（由 `electron-builder.yml` 的 `publish` 段生成）|
| 当前分发通道（M34）| `provider: github` → 公开仓库 `kevinLei736/FlowProbeClient` 的正式 Release。源码仓库 `kevinLei736/FlowProbe` 保持私有 |
| 占位地址识别 | 1.20.0 及更早的包里 `publish.url` 是 `https://update.invalid/flowprobe/`。识别到该占位域名时回「发布方尚未启用更新服务」，而不是抛域名解析错误 |
| 启动自查 | 默认开，启动后延迟 8 秒执行 |
| 自动下载 | 默认关，发现新版本后由用户点「下载新版本」 |
| 下载进度 | 百分比 + 已传/总大小 + 实时速率 |
| 安装 | 「重启并安装」= 非静默安装 + 装完自动重启 |
| 状态外露 | 菜单项文案三态：检查更新… / 有新版本… / 有新版本可安装… |
| 配置存储 | `userData/update.json`，只存两个开关，原子写（tmp + rename）|

**实现要点（为什么这样做）**

| 决策 | 原因 |
|------|------|
| 地址由打包决定，不做运行时配置 | 见上文「为什么收缩」。可配置把发布方的一次性决定变成每个使用者的必答题，而答错的反馈信号（404）没有区分度 |
| 不调用 `setFeedURL()` | 地址已在安装包内的 `app-update.yml` 里，库自己读得到。再设一遍等于让同一个地址有两个来源，两处不一致时排查成本极高 |
| 识别 `update.invalid` 占位域名并给专门文案 | 「发布方还没接更新服务」与「你的网络有问题」是两件不同的事。混成同一个网络错误会让人白查半天网络 |
| 解析 `app-update.yml` 只手工取 `url:` 一行，不引 yaml 库 | 要读的只有一个字段，为此多一个依赖不值得。读不到就当没有，不影响 electron-updater 自己工作（它读的是同一个文件）|
| 读取旧配置时直接丢弃 `feedUrl` / `githubRepo` / `githubProxy` | 这些字段已无对应功能。做「迁移」反而会让人以为还能生效；报错则会让老用户的配置文件变成启动阻碍 |
| 产物名固定为不含空格的纯 ASCII（`FlowProbe-Setup-${version}.${ext}`）| 默认产物名带 `productName` 与空格，而分发环节（GitHub Releases 上传等）会改写文件名，`latest.yml` 记的却是原始名字，一旦被改写下载必然 404 |
| 错误文案不再让用户「检查地址」 | 他没有地址可改。能做的只有查网络或等发布方修好服务器，提示要指向这两件事 |
| 状态用一个扁平 `phase` 字段，而非多个布尔量 | 六种状态本质互斥，布尔量组合迟早出现「既在下载又已是最新」的矛盾态，界面就得写优先级判断 |
| `electron-updater` 惰性 `require`，不做顶层 import | 未打包环境下它的构造过程本身可能抛错，顶层引入会连累主进程起不来。可选功能不该有能力拖垮应用启动 |
| 自动下载默认关闭 | 下载完终究要重启才生效，而重启会掐断所有正在运行的连接与监听端口。调试台经常挂着长连接抓现场，静默下载会让「什么时候能重启」变成一个被动决定 |
| 启动检查延迟 8 秒 | 启动瞬间正在恢复会话、开监听端口、初始化 SQLite 历史库，此时发网络请求与磁盘写入会抢 I/O，拖慢首屏可用时间 |
| `autoInstallOnAppQuit = false`、`allowDowngrade = false` | 退出时静默装，用户下次启动会看到「版本莫名变了」；允许降级则一次误传旧 `latest.yml` 会把所有人拖回旧版 |
| 两个开关单独存 `update.json`，不进 workspace | 工作区会导出给同事、跟着项目走；这两个开关属于这台机器上的个人偏好 |
| 失败原因分类翻成中文处置建议 | 域名解析不了 / 连不上 / 404 或缺 `latest.yml` / sha512 不匹配 / 证书不受信，对应动作完全不同，原样抛英文栈等于没提示 |
| 错误码同时匹配 Node 与 Chromium 两套 | `electron-updater` 的网络请求走 Electron 的 `net` 模块，失败时给的是 `net::ERR_NAME_NOT_RESOLVED` 这类 Chromium 码，**不是** Node 的 `ENOTFOUND` |
| 更新说明按纯文本渲染 | 该文本来自服务端，不应具备往界面插标签的能力 |
| 未打包时明确回「开发运行不检查更新」，而不是静默失败 | 若装的是安装版却看到这句，说明启动的是错的目标 |
| `quitAndInstall` 放进 `setImmediate` | 让 IPC 回执先发回渲染进程，否则界面会停在「正在重启…」之前的状态上 |
| 状态用主动推送（`update:event`）而非渲染层轮询 | 下载进度是高频连续量，轮询要么卡顿要么浪费；且菜单栏文案也要跟着变，事件源只该有一处 |
| 更新状态订阅提在应用外壳，不放在面板内部 | 菜单项要显示结论，而面板大部分时间是关着的 |

**更新服务器要求**：一个能按路径返回文件的静态服务即可（Nginx / 对象存储 / 内网文件服务），目录下放 `latest.yml`、`.exe`、`.blockmap` 三个文件，均由 `npm run dist` 生成。缺 `latest.yml` 的后果是静默的 —— 客户端不报错，只一直显示「已是最新版本」。

**发布流程**：改 `package.json` 的 `version` → `npm run dist` → 把 `release/` 下三个文件上传到更新目录。若拿公开 GitHub 仓库的 Release 当静态目录，可用 `npm run release`（= `dist` + `publish:github`）。

发布脚本 `scripts/publish-github.mjs` 的实现取舍：

| 决策 | 原因 |
|------|------|
| 自己写而不用 `electron-builder --publish always` | builder 会连带重新打包（产物已经在手上了），且它默认「代码仓库 = 发布仓库」，而这里恰恰要把两者分开 |
| 只用内置 `fetch`，零第三方依赖 | 发布脚本会在 CI 或同事机器上跑，多一个依赖多一处失败点 |
| 令牌从 `.env` 读（已 gitignore），不硬编码不逐次手敲 | 令牌进仓库是安全事故；每次 export 一遍则会让人图省事写进脚本 |
| 动手前先探测仓库可达性与可见性 | 权限不足的报错出现在上传第三个文件时最难理解；发布仓库是私有的更要提前拦，否则整套流程走完才发现自动更新根本取不到文件 |
| tag 已存在则复用 Release | 上一次传到一半失败必须能直接重跑，而不是先去手工删 Release |
| 同名附件先删再传，而非跳过 | 重发同一版本通常正是因为上次传坏了，跳过会把坏文件留在线上 |
| 流式上传（`createReadStream` + `duplex: 'half'`）| 安装包接近百兆，整体读进内存没有必要 |
| 五个 dist 脚本统一 `--publish never` | 打包与上传拆成两步，可以只打包不发布；上传由专门脚本负责 |

若用 GitHub Releases 当分发通道，发布仓库必须**公开**：私有仓库的 Release 附件需带令牌才能下载，自动更新取不到；而把令牌打进客户端等于公开它。代码仓库仍可私有。详见 [发布与自动更新](发布与自动更新.md)。

**验证方式**：见 §3.34。

### 3.33 品牌命名与数据兼容（已实现 · M32）

**动机**：「调试小工具」是开发期的占位名，说不清工具在做什么，也无法作为安装包与仓库名对外。改名为「探流 / FlowProbe」——报文在链路上流动，工具在链路中间下探针把每一帧截下来看清楚。

**命名落点**：

| 位置 | 旧值 | 新值 | 说明 |
| --- | --- | --- | --- |
| `package.json` `name` | `debug-toolbox` | `flowprobe` | 决定 Windows/Linux 的 userData 目录名 |
| `electron-builder.yml` `appId` | `com.debugtoolbox.app` | `com.flowprobe.app` | 系统层应用标识、卸载注册项 |
| `productName` / `shortcutName` | 调试小工具 | 探流 →（M33）FlowProbe | 窗口标题、快捷方式、dmg 卷标 |
| Windows 产物名 | `DebugToolbox-Setup-*.exe` | `FlowProbe-Setup-*.exe` | 仍为纯 ASCII（见 §3.32 的 404 原因） |
| mac 产物名 | `DebugToolbox-*.dmg` | `FlowProbe-*.dmg` | 同上 |
| 录制文件 `format` | `debug-toolbox-recording` | `flowprobe-recording` | 读取端双认，见下 |
| HAR `creator.name` | 调试小工具 | 探流 →（M33）FlowProbe | 导出的 HAR 里的工具署名 |
| 自签证书默认 O 字段 | 调试小工具 | 探流 →（M33）FlowProbe | 用户未填组织名时的兜底 |

**改名的三处兼容性风险与处置**：

| 风险 | 根因 | 处置 |
| --- | --- | --- |
| 老用户「升级后数据全没了」 | Electron 的 `userData` 目录名取自 `package.json` 的 `name`；改名后应用指向一个全新空目录，而 `workspace.json`、`history.db`、`update.json`、`certs/` 都还在旧目录 | 新增 `src/main/userDataMigration.ts`：首次启动把这几项从旧目录**复制**到新目录，写哨兵文件 `.migrated-from-debug-toolbox` 防重复搬 |
| 旧录制文件打不开 | `.json` 里的 `format` 字段是加载准入判断依据 | 写入只用新标识，读取同时接受旧标识（`ACCEPTED_FORMATS`）；`RecordingFile.format` 因此是两值联合类型 |
| 已发布客户端下载 404 | 旧客户端按旧 `latest.yml` 记的文件名取包 | 改名这一版在 Release 里保留一份旧名副本，或通知用户手动装一次 |

**设计取舍**：

| 取舍 | 理由 |
| --- | --- |
| 迁移用复制而不是移动 | 迁移出错或版本回退时旧目录还在原地，用户能装回旧版继续用。代价只是磁盘上多一份历史库 |
| 迁移调用放主进程模块顶层，不放 `whenReady` | `SessionManager` 在模块作用域就 `new HistoryStore()`，历史库路径已经指向新 userData。等到 `whenReady` 再搬，新目录可能已生成空的 `history.db`，迁移会因「目标已存在」整段跳过 |
| 只搬 6 项，不整目录复制 | `Cache`、`GPUCache`、`Local Storage` 等是 Chromium 自建缓存，跨目录复制既慢又无意义，它们会自动重建 |
| 用哨兵文件判断而非「目录是否为空」 | Electron 在 `whenReady` 之前就会往 userData 写 `Preferences`、`DevToolsActivePort`，用「空目录」当条件必然漏判 |
| 目标已存在则跳过该项，不覆盖 | 用户可能先在新版本里建了会话再回头装旧版数据，覆盖等于吃掉新数据 |
| `package.json` 不加 `productName` 字段 | `app.getName()` 优先读 `productName`，填中文会让 userData 变成中文路径，原生模块与命令行都容易踩坑。中文名只写在 electron-builder 配置里，仅影响展示层 |
| 迁移失败只记日志不弹窗 | 迁移不是启动的必要条件，最坏结果是从空工作区重建会话；为此拦住启动得不偿失 |

**Logo 重绘**：三条数据流线 + 中间一条在环形探针处断开。旧图标是紫蓝渐变的信号波形，与界面 `--accent` 的无彩色令牌（深色 `#ececf0` / 浅色 `#1f2329`）不一致。新图标只用粗直线与一个圆环 —— 这枚图标最小要在 16px 托盘里渲染，曲线、渐变、发光在该尺寸会糊成一团灰。界面 Logo 组件取色一律走 `var(--accent)` 与 `var(--bg-1)`，深浅主题自动反相。`build/icon.icns` 改为纯 Node 拼装（icns 只是「魔数 + 若干 类型/长度/PNG 块」的容器），不再依赖 macOS 的 `iconutil`。

**验证方式**：全仓 65 处旧名逐一核对替换，剩余 5 处均在「兼容旧值」的说明文本里。`tsc --noEmit` 双配置 0 错误。开发版实测：窗口标题 `探流`、关于面板署名「探流」、数据路径显示 `…\Roaming\flowprobe\workspace.json`；迁移哨兵内容 `copied: [workspace.json, update.json, history.db, history.db-shm, history.db-wal, certs]`，新目录 `workspace.json` 3609 B 与旧目录一致、`history.db` 7,098,368 B，旧目录仍在原地未被删。深浅两主题分别截图核对标题栏 Logo（深色近白、浅色近黑）与关于面板。图标 16/32/48/64/256 五档缩略图核对，16px 下三条线与探针缺口仍可辨。

### 3.35 分发通道落地：双仓库 + GitHub 自动更新（已实现 · M34）

M33 把更新地址收敛成「打包时决定」，但当时 `publish.url` 还是占位域名 `update.invalid`，
也就是说通道本身还没接上。M34 把它接到真实的 GitHub 发布通道。

#### 一、为什么是两个仓库

| 仓库 | 可见性 | 放什么 | 谁访问 |
|------|--------|--------|--------|
| `kevinLei736/FlowProbe` | **私有** | 源码、文档、构建脚本 | 只有开发者 |
| `kevinLei736/FlowProbeClient` | **公开** | 每版安装包与版本清单（Release 附件）| 所有使用者的客户端 |

自动更新必须能**匿名**下载附件。私有仓库的 Release 附件每次请求都要带令牌，
而把令牌打进客户端等于公开它 —— 任何人解包 asar 都能拿到，且这枚令牌还带着源码仓库的读权限。
所以「代码私有 + 安装包公开」不是偏好，是唯一站得住的组合。公开的那个仓库里只有二进制，不含一行源码。

#### 二、provider 选型：github 而非 generic

两种接法都能work，取舍如下：

| 方案 | 代价 |
|------|------|
| `generic` + `https://github.com/…/releases/latest/download/` | 每次取文件都要穿一层 302 跳转；部分网络环境下跳转会让 blockmap 增量下载退化成整包下载；Release 正文拿不到，更新面板里没有「这版改了什么」|
| **`github` + owner/repo（采用）** | 直接读 Release 元数据，正文能显示在面板里；增量下载不经跳转 |

并加 `releaseType: release`：草稿与预发布不推给所有人，否则一次试验性发布会让全员弹更新提示。

#### 三、客户端侧的适配

M33 的 `packagedFeedUrl()` 只解析 `app-update.yml` 里的 `url:` 一行 —— 而 github provider 写进去的是
`owner` + `repo`，根本没有 `url` 字段。若不改，装上新包反而会判定成「这个安装包没有内置更新地址」。

| 改动 | 原因 |
|------|------|
| `packagedFeedUrl(): string` → `packagedFeed(): { provider, url, owner, repo }` | 两种 provider 的地址字段不同名，只认 `url` 会把 github 包误判成没接更新 |
| 可用性判定改为 `(owner && repo) || url` | 「有 owner 和 repo」与「有完整 url」都算接上了通道 |
| 保留 `update.invalid` 占位判断 | 已经装了 1.20.0 及更早包的人，包内写的还是占位域名。他们点检查更新应当看到「发布方尚未启用更新服务」这句人话，而不是域名解析错误 |
| 新增错误分类「发布仓库里还没有正式版本」 | 匹配 `ERR_UPDATER_LATEST_VERSION_NOT_FOUND` 等。这是 GitHub 通道特有的状态（仓库建好但一个 Release 都没发），既不是网络问题也不是 404，混进去会让人白查网络 |

#### 四、一次性的升级断点

1.20.0 及更早的安装包内置的是占位地址，**它们无法自动升到 1.21.0** —— 这一版必须手动装一次。
装过 1.21.0 之后，后续所有版本都走自动更新。这个断点无法回避：更新地址在包内，
而改地址本身就需要发一个新包，老包里不可能预先知道未来的地址。

#### 五、凭据与安全边界

| 项 | 处置 |
|----|------|
| 发布令牌 | 放项目根 `.env`（`DT_GITHUB_TOKEN`），已在 `.gitignore` 里。脚本按 `DT_GITHUB_TOKEN` → `GH_TOKEN` → `GITHUB_TOKEN` 顺序取 |
| 令牌权限 | 经典令牌 `repo` 域。同一枚令牌既推私有代码仓库，也上传公开发布仓库的附件 |
| 客户端 | **不含任何令牌**。下载走匿名公开链接 |
| 私有仓库误配保护 | 发布脚本探测到发布仓库是私有时当场警告 —— 那种情况下自动更新一定取不到文件，且失败信号是静默的 |

#### 六、落地实测结果

| 检查项 | 实测 |
|--------|------|
| 令牌权限 | `/user` 返回 scopes 含 `repo`；两仓库 `admin: true` |
| 仓库可见性 | `FlowProbe` `private: true`、`FlowProbeClient` `private: false` |
| 包内更新源 | `app-update.yml` = `provider: github` / `owner: kevinLei736` / `repo: FlowProbeClient` / `releaseType: release` |
| Release | `v1.21.0`，`draft: false`、`prerelease: false`，三个附件（exe 90,232,917 B、blockmap 92,244 B、latest.yml 349 B）|

| 安装版检查更新 | `phase: up-to-date`（本机已是 1.21.0，说明清单读到了且版本比对生效，不是占位或报错）|
| 代码仓库内容 | 176 个条目，`.env` 与 `release/` 返回 404（确认未上传）|

#### 七、踩到的两个坑（写下来是为了下次不再重踩）

| 现象 | 根因 |
|------|------|
| 发布脚本首跑 HTTP 422 `Repository is empty` | GitHub 不允许在**空仓库**上建 Release —— tag 需要一个提交作为落点。用 Contents API 直接写一个 README 建立初始提交即可，不必为此在本地克隆一个仓库 |
| `git push` 连续五次 `Failed to connect to github.com port 443`，而 `api.github.com` 与 `raw.githubusercontent.com` 同期正常 | 国内到 github.com 的连通性是**间歇性**的，且各子域走不同的边缘节点。所以「API 通」推不出「git 能推」。加重试即可，不必换方案；而 `gh-proxy` 一类镜像只代理匿名读，**不转发 Git 认证**，用它推送必然报 `Invalid username or token` |

#### 九、端到端升级实测（M35）

前面验的只是「已是最新版本」—— 那只能证明清单读到了，不能证明升级路径通。
于是留一份 1.21.0 的免安装副本当「旧客户端」，发一版 1.21.1，让它自己去发现并下载。

| 阶段 | 实测 |
|------|------|
| 发现新版本 | 旧客户端启动后自动检查（延迟 8 秒）即进入 `phase: available`、`newVersion: 1.21.1`，无需手动点 |
| 拿到发布说明 | `releaseNotes` 有内容 —— 证实了选 `github` provider 而非 `generic` 的收益（generic 只读 `latest.yml`，拿不到 Release 正文）|
| 下载 | 90,232,798 B 全量下完，`percent: 100`，速率约 2.5 MB/s |
| 完整性 | 下载文件的 sha512 与 `latest.yml`、与 updater 自己记的 `update-info.json` **三处一致** |
| 落盘位置 | `%LOCALAPPDATA%\flowprobe-updater\pending\`（由 `updaterCacheDirName` 决定）|

刻意没有点「重启并安装」：那会杀掉进程，后续所有调试通道断线，无法取证。
安装这一步的正确性由 electron-updater 的 NSIS 流程负责，且下载完整性已在上一行确认。

#### 十、顺带修掉的一个显示缺陷

实测第一次看到 `releaseNotes` 时，内容是 `<h3>FlowProbe v1.21.1</h3><p>Windows：下载 <code>…`。

**根因**：更新面板刻意按纯文本渲染发布说明（那段文字来自服务端，不该有能力往界面插标签），
而 GitHub 的 Release 正文经 API 返回时**已经是渲染好的 HTML**。两个正确的决定相遇，
结果是用户看到一堆标签字面量。

所以问题不在「要不要转义」—— 转义本来就做了。缺的是把标签**语义**还原成排版：
主进程侧新增 `htmlToText()`，块级标签变换行、`<li>` 变短横线、HTML 实体还原、多余空行塌陷。
放在主进程而不是渲染层，是因为 `normalizeNotes()` 已经是「把服务端各种形态的说明统一成一段文本」的收口点，
再往下游加一层等于让同一件事有两个负责人。

实测输入那段 HTML，输出 7 行纯文本、无任何尖括号残留。
#### 十一、发布脚本的上传重定向缺陷（M35 实测暴露）

发 1.21.2 时首个附件即失败：`HTTP 307 Moved Permanently`。

**根因**：请求体是一个**流**，而流只能被消费一次。GitHub 偶发返回 307 要求换地址重发，
`fetch` 内置的跟随重定向此时拿不到可重放的 body，于是把 307 原样抛回调用方。
这不是权限或网络问题 —— 前两次发布（1.21.0、1.21.1）没撞上纯属运气。

| 改动 | 原因 |
|------|------|
| `redirect: manual` + 手动重发 | 每次重发新开一个 `createReadStream`，流的一次性消费问题自然消解 |
| 上传地址优先取 Release 响应里的 `upload_url` 模板 | 那是 GitHub 当次给出的规范地址；自己拼的 `uploads.github.com/...` 在后端调整时就会开始收重定向 |
| 5xx 与网络中断也重试（最多 4 次，退避 2/4/6 秒）| 百兆文件在国内到 GitHub 的链路上断一次很常见，重试的代价远低于整次发布失败后人工重跑 |
| 4xx 不重试 | 那是我们自己的问题（名字重复、权限不足），重试只会把真正的原因埋在四条重复日志下面 |

修完连发 1.21.2、1.21.3 两版，三个附件均一次通过。
#### 十二、GitHub 账号名变更（1.21.4）

推送 1.21.3 时 GitHub 回了一句 `This repository moved. Please use the new location`：
账号 `LeiQinLin` 已改名为 `kevinLei736`。旧路径仍能用（GitHub 会永久重定向），但**不能依赖它**：

| 位置 | 处置 |
|------|------|
| `electron-builder.yml` 的 `owner` | 必须改。它会写进安装包内的 `app-update.yml`，是客户端唯一的更新源坐标 —— 依赖重定向意味着每次检查更新都多一跳，且一旦对方回收旧名，所有已发出去的客户端同时失联 |
| `.env` 的 `DT_RELEASE_REPO` / `DT_CODE_REPO` | 改。发布脚本按这个名字调 API |
| `git remote origin` | 改。否则每次 push 都打一行 moved 警告 |
| README 与两份文档里的仓库链接 | 改。文档里的失效链接比没有链接更误导人 |

全仓核对后 `LeiQinLin` 零残留（`package-lock.json` 不含该字符串）。

#### 八、凭据处置

推送时把令牌写进 `.git/.tcred`（`credential.helper=store --file=`）而不是远端 URL 或命令行参数：
URL 里的令牌会永久留在 `.git/config` 并被 `git remote -v` 直接打在屏幕上，命令行参数会出现在进程列表里。
推送成功后立即删除该文件，并已核对 `.git/config` 内不含 `ghp_` 与 `credential` 字样。

### 3.36 发布仓库门面：中英双语 README（已实现 · M36）

#### 一、为什么要单独写一份

发布仓库 `FlowProbeClient` 只放安装包，建仓时为了绕开「空仓库不能建 Release」的限制，用 Contents API 草草写了 25 行 README。
但对下载者来说，这个页面就是产品的第一屏也往往是唯一一屏 —— 他们不会打开源码仓库（私有），也不会先装上再看内置手册。
所以这份 README 的职责不是仓库说明，而是**替代产品官网**：先答「这是什么、能替我省掉哪几个工具」，再答「装哪一个文件」，最后答「出问题先查什么」。

中英双语的取舍：**应用界面仍是简体中文**，英文版只是让非中文使用者能判断要不要装，因此英文版在顶部明确标注界面语言，避免下载后才发现看不懂。
两份文件互挂语言切换链接（`README.md` ⇄ `README.en.md`），GitHub 默认渲染 `README.md`，所以中文版是主入口。

#### 二、结构与信息顺序

| 段落 | 承担的问题 | 关键取舍 |
|------|-----------|---------|
| 居中标题块 | 这是什么 | 一句话定位 + release badge（`shields.io` 直读 latest tag，发版后自动变，不必手工改版本号）|
| 名字来源 | 为什么叫这个 | flow（报文在链路上流动）+ probe（在链路中间下探针），一句话讲完 |
| 下载与安装 | 装哪个文件 | 三平台表格；**显式说明 `latest.yml` / `.blockmap` 不需要手动下载**（否则用户会以为漏了文件）；已装用户直接引导到「帮助 → 检查更新」，不必回仓库；macOS ad-hoc 签名的「仍要打开」提示写在这里而不是 FAQ，因为它是必经步骤 |
| 模块与可用功能一览 | 哪个模块有哪些能力 | 连接类模块用**矩阵表**（模块 × 收发 / 定时发送 / 结束符 / 切帧 / 心跳 / 重连 / 多对端），一眼看出边界；服务测试类与分析类按「核心能力 + 关键可用项」列。矩阵里的「—」额外解释成「协议不提供」而非「没做」|
| 功能详解 | 每项具体怎么用、有哪些可选值 | 十一个小节（TCP/UDP、WebSocket、串口、MQTT、Modbus 主站、Modbus 从站、HTTP Mock、接口测试、报文分析、告警、历史与看板、工作区、自动更新），可选值列成表：波特率档位、五种校验、点表七列、Mock 四种路径匹配、模板占位符清单、四类断言…|
| 常用快捷键 | 怎么快 | 12 行，只收高频项；注明 macOS 上 `Ctrl` 读作 `⌘`，完整表交给应用内 |
| —（刻意不写）| — | **不描述界面**：不讲左中右三栏、标签页、分屏、主题、密度缩放、输入区拉伸。这些是用起来自然会遇到的东西，写进 README 只会把「能不能解决我的问题」这个真问题挤到下面去 |
| 数据存在哪 | 会不会上传 | 明确「只存本机、不上传」+ 双平台路径 + 指向「文件 → 打开工作区所在目录」，方便备份迁移 |
| 常见问题 | 出问题先查什么 | 7 行「现象 → 先查这里」，含 1.20.0 及更早需手动装一次的历史包袱说明（见 §3.35）|

#### 三、上传方式与一处约束

两份 README 通过 Contents API 写入（`scripts/publish-client-readme.mjs`），而不是把发布仓库也 clone 下来：
发布仓库在本地没有工作副本，为一次文档更新去建一个副本会多出一份需要同步的状态。

约束是**覆盖已有文件必须带该文件当前的 `sha`**，否则 GitHub 返回 422；新建文件反而不能带。
脚本因此先 `GET /contents/<name>` 探测：拿到 `sha` 就走覆盖，404 就走新建。

源文件留在代码仓库 `client-readme/` 下版本管理，线上那两份视为构建产物 —— 下次改动有源可依，也能 diff 出改了什么。

#### 四、实测结果

| 项 | 结果 |
|----|------|
| `README.md` 覆盖 | HTTP 200（带既有 sha）|
| `README.en.md` 新建 | HTTP 201（不带 sha）|
| 匿名回读中文版 | 200 · 10,846 字符 · 360 行 · 无替换字符（编码正常）|
| 匿名回读英文版 | 200 · 24,342 字符 · 360 行 · 无替换字符 |
| 语言切换行 | 中文版 `[English](README.en.md) · 简体中文`；英文版 `English · [简体中文](README.md)` |
| release badge | `shields.io` 返回 200 · `image/svg+xml` |

两版行数一致（360）是刻意的：段落与表格一一对应，改动其中一版时容易发现另一版漏改。

#### 五、回读失败不判失败（实测踩到）

首轮回读时 `raw.githubusercontent.com` 连接超时（`UND_ERR_CONNECT_TIMEOUT`，`185.199.108.133:443`），而写入的 `api.github.com` 同期一切正常 —— 与 §3.35 记的连通性间歇是同一现象。
脚本因此改成：回读重试 3 次、退避 2/4 秒；**三次都失败只告警不置失败码**。
理由是写入已经拿到 200，把发布结果绑在一条本机易抖的链路上只会产生误报，而误报会让人开始怀疑真正成功的那一步。


### 3.37 文档职责分层与多平台发布（已实现 · M37）

#### 一、为什么要拆文档

此前功能清单有两份：主 `README.md`（1305 行，含三十节功能详解）与发布仓库的门面说明。
同一个功能两处描述，改一处忘一处，而读者无从判断该信哪一份 —— 这类偏差最难发现，因为两处单独看都是通顺的。

拆法是按**读者身份**分，不按内容多少分：

| 文档 | 读者 | 只回答 |
|------|------|-------|
| `client-readme/README.md`（+ `.en.md`）| 下载者 | 有哪些模块、每个模块能做什么、可选值有哪些 |
| `docs/使用文档.md` | 使用者 | 具体怎么操作、界面在哪点、出问题怎么查 |
| `README.md` | 开发与维护者 | 架构、**为什么这样实现**、怎么打包、怎么发布 |
| `docs/需求与架构设计.md` | 维护者 | 需求边界、模块拆分依据、里程碑 |
| `docs/发布与自动更新.md` | 发布者 | 双仓库分工、发版步骤、排查表 |

主 README 从 1305 行降到 520 行，删掉的**全部是功能罗列**（那些内容在客户端 README 里更完整），保留并扩写的是设计取舍。
判断标准很直接：一句话如果换个人来写会写成一样的（「支持 GET / POST / PUT」），它属于功能清单；如果换个人可能写成相反的（「服务端监听失败不退避重连」），它属于架构文档。

新增「模块与代码位置对照」表，从功能反查代码时用 —— 这是主 README 独有的信息，两份使用者文档都不该有。

#### 二、多平台发布：跨平台打包不成立

原生模块（`better-sqlite3`、`@serialport/bindings-cpp`）必须按目标平台与 Electron 的 ABI 编译，所以一个版本要覆盖 Windows 与 macOS，只能在两台机器上各打一次，再合进同一个 Release（同一个 `v<version>` tag）。

原发布脚本挡在这条路上：它维护一张**扁平的必需/可选清单**，把 `latest.yml` 写成必需项。
在 mac 上执行时 `release/` 里根本不会有 `latest.yml`（那是 Windows 清单），脚本直接报「找不到 latest.yml，先执行 npm run dist」而退出 —— 提示还把人往错误方向引。

改成**按平台分组判定**：

| 判定 | 规则 |
|------|------|
| 平台是否参与本次发布 | 该平台的安装包存在任意一个 |
| 参与了却缺清单 | 直接报错。清单缺失的后果是静默的：客户端不报错，只显示「已是最新版本」 |
| 两个平台都不参与 | 才判定为「还没打包」|

#### 三、Release 正文按平台做并集

复用同名 Release 时，正文不能直接覆盖也不能完全不动：
覆盖会抹掉先发那次写的 Windows 安装说明，不动则 macOS 说明永远不出现。

所以 `buildNotes()` 只生成本次实际上传平台的段落，新增 `mergeNotes()` 按平台段落取并集 —— 已有正文里没出现的段落才追加，出现过则原样保留（避免每次发布都改动正文）。
在正文里列一个还没上传的文件名，等于让人去点一个 404。

#### 四、mac 自动更新读 zip 不读 dmg

这一点最容易漏：只传 dmg 的话新用户能正常下载安装，但已装用户的「检查更新」永远查不到新版本，且界面只显示「已是最新版本」，没有任何报错。
`npm run dist:mac` 两者都会产出，脚本已把 zip 列进 macOS 组，不依赖发布者记得挑。

#### 五、实测结果

| 项 | 结果 |
|----|------|
| 主 README | 1305 → 520 行，五个内部链接全部可达，代码围栏 26 处配平 |
| 发布脚本语法 | `node --check` 通过 |
| 仅有 Windows 产物时 | 正确识别为「Windows（3 个文件）」并继续 |
| 移开 `latest.yml` 后 | 报「找到了 Windows 安装包，但缺少 latest.yml」并说明后果是静默的 |
| 令牌无效时 | 在动手上传前就以 401 退出 |
| 正文并集幂等性 | 首版按整行比对，给平台名加粗后被判成缺失，追加了第二遍（线上实测）。改按平台关键字判断后，连续两次发布正文不再变动 |


#### 六、并集判断不能按整行比对（实测踩到）

首版 `mergeNotes()` 拿新生成的整行去 `oldBody.includes(line)` 比对。
看着更严谨，实际很脆：这一轮顺手把平台名加粗成 `**Windows**`，于是与线上正文里的旧写法不再相等，被判成「没讲过 Windows」，同一段说明被追加了第二遍 —— 线上真的出现了重复段落。

改成按**平台关键字**判断（正文里出现过 `Windows` 就不再追加 Windows 段落）。
文案措辞是会变的，平台名不会；判断条件应该盯住不变的那部分。
修完连续跑两次发布，第二次正文零改动，幂等性成立。

## 4. 界面设计（Codex 风格）

- **整体**：与 ChatGPT / Codex 桌面版一致的中性外观。三档主题（跟随系统 / 浅色 / 深色），**无彩色强调色**（早期草案的青绿已废弃），状态靠明度与字重区分；报文区等宽字体，UI 文案无衬线。
- **左栏**：会话列表 + 预设库 + 新建连接入口，图标化协议类型。
- **中栏**：顶部连接状态条（地址、状态、统计）→ 报文时间轴 → 底部发送编辑器（格式切换 + 发送按钮）。
- **右栏（检查器）**：当前会话的完整设置项，随协议类型动态变化；折叠分组。
- **顶部菜单栏**：自绘标题栏 + 文件/会话/视图/工具/帮助五组系统功能，右侧为最小化/最大化/关闭三键（详见 4.1）。
- **命令面板**：Ctrl+K 呼出，模糊搜索命令与会话。

### 4.1 系统功能与模块功能划分（M21 重构）

早期版本把「主题切换」「导入导出」「看板入口」这些和会话无关的操作塞在左栏底部，
和「选会话」这件事抢注意力。M21 起按**操作对象**做硬性划分：

| 类别 | 判定标准 | 承载位置 | 内容 |
|------|----------|----------|------|
| **系统功能** | 作用于应用本体，与当前是哪个会话无关 | **顶部菜单栏** | 窗口控制（最小化/最大化/关闭）、视图布局（左栏/检查器）、主题三档、密度三档、缩放、数据目录定位、配置导入导出、重启、使用文档与快捷键、关于、检查更新（开发者工具仅开发运行时出现） |
| **模块功能** | 作用于某个协议/某个会话，操作对象就在眼前 | 左栏 / 中栏 / 右栏原位 | 连接参数、收发编辑器与片段、Mock 路由与场景、接口测试断言、协议解析模板、分组与标签 |

菜单栏分五组：**文件 / 会话 / 视图 / 工具 / 帮助**。菜单定义做成纯数据模型
（`MenuItem { label, hint, run, checked, radio, disabled, danger }`），
同一份定义同时供菜单栏与命令面板消费，避免两处入口功能不一致。
`MenuContext` 携带 `hasSession / running / sidebarVisible / inspectorVisible / theme / density`，
菜单项的禁用与勾选态由上下文推导，不在组件里写分支。

左栏职责因此收窄为「找会话 + 切会话」：新建按钮、搜索、标签筛选、分组列表，
底部仅保留看板 / 历史 / 搜索 / 接口测试 / 工具箱五个图标快捷入口。

### 4.2 窗口最大化被禁用的根因（实测）

现象：自绘标题栏的最大化按钮点了没反应，`win.isMaximizable()` 返回 `false`。
用一个最小 Electron 工程逐项做探针，结论如下：

| BrowserWindow 配置 | isMaximizable |
|--------------------|---------------|
| `transparent: true` | **false** ← 根因 |
| `backgroundMaterial: 'acrylic'`（单独） | false |
| `backgroundColor: '#00000000'`（单独） | true |
| `titleBarStyle: 'hidden'` + `backgroundMaterial: 'acrylic'` | **true** ← 采用方案 |
| `transparent: true` 之后再 `setMaximizable(true)` | true（可强行恢复） |

原因是 Windows 上透明窗口走**分层窗口（layered window）**路径，
Electron 为规避分层窗口下最大化的绘制问题，直接把 `maximizable` 一并关掉。

最终窗口配置：`frame: false` + `titleBarStyle: 'hidden'` + `backgroundMaterial: 'acrylic'`
+ `backgroundColor: '#00000000'` + `maximizable: true`，并在窗口创建末尾补一次 `setMaximizable(true)` 兜底；
同时 `Menu.setApplicationMenu(null)` 去掉原生菜单，避免和自绘菜单栏重复。
视觉上仍是背板透 + 亚克力模糊，但最大化、双击标题栏、拖到屏幕顶部贴边全部恢复正常。

主进程通过 `window:state` 与 `window:event` 把 `WindowState { maximized, fullScreen, focused }`
推给渲染层，标题栏按钮图标据此切换（还原 / 最大化）。

### 4.3 跨平台窗口适配（macOS / Windows）（已实现 · M26）

毛玻璃与标题栏在两个平台是**两套互不通用的 API**，混用会出现「配置写了但没生效」
或按钮互相遮挡：

| 能力 | Windows | macOS |
|------|---------|-------|
| 毛玻璃背景 | `backgroundMaterial: 'acrylic'` | `vibrancy: 'under-window'` |
| 隐藏标题栏 | `titleBarStyle: 'hidden'` | `titleBarStyle: 'hiddenInset'` |
| 窗口按钮 | 需自绘（最小化/最大化/关闭） | 系统红绿灯，**不可自绘** |
| 修饰键 | `Ctrl` | `⌘`（Command） |

三个关键决策：

1. **mac 用 `hiddenInset` 而非 `hidden`**。`hidden` 会把红绿灯顶到最左上角，
   正好压住自绘菜单栏的 Logo；`hiddenInset` 让它们内缩，再配合渲染层给 brand 区
   留出 74px 左内边距（`MAC_TRAFFIC_LIGHT_WIDTH`），两者不再重叠。
2. **mac 上不渲染那三个自绘按钮**，否则与系统红绿灯功能重复。判断依据是 preload
   同步注入的 `platform`，而不是异步的 `appInfo()` —— 后者首帧拿不到值，会导致
   按钮先渲染一帧再消失。
3. **按键提示集中到 `app/meta.ts` 的 `keyHint()` / `MOD`**。原先 `'Ctrl+X'` 写死在
   8 个文件里；键盘处理本身早就同时认 `ctrlKey || metaKey`，差的只是显示文案，
   因此只在显示层翻译，不动任何按键判断逻辑。常量仍以 Windows 写法作为「源格式」。

Windows 侧行为经实测确认未回归：`platform=win32` 时按钮仍为 3 个、
左内边距仍为 10px、最大化状态切换 `false → true → false` 正常、提示仍显示 `Ctrl`。

#### macOS 打包链路

| 环节 | 处理 | 为什么 |
|------|------|--------|
| 图标 | `build/icon.icns`（由 `icon.png` 生成） | mac 不认 `.ico` |
| 产物 | `dmg` + `zip`，`arm64` + `x64` | dmg 给人装，zip 给自动更新/解压用 |
| 签名 | `identity: null` + `afterSign` 钩子做 ad-hoc 签名 | **Apple Silicon 内核会直接杀掉签名无效的进程**，不签名等于必闪退；无证书时 `codesign -s -` 即可满足内核校验 |
| 权限 | `build/entitlements.mac.plist` | V8 需要 JIT 与可写可执行内存；本工具还需网络监听与串口访问 |
| 原生模块 | `npm run setup:mac` | 见下 |

**原生模块是跨平台最大的坑**。`better-sqlite3` 没有预编译包，且必须按
**Electron 的 ABI** 编译（本机 `build/config.gypi` 里 `runtime: electron`、`target: 31.7.7`），
而 `npm install` 默认编出来的是 Node ABI，直接用会报 `NODE_MODULE_VERSION` 不匹配。
`@serialport/bindings-cpp` 反而自带 `darwin-x64+arm64` 预编译包，不受影响。

更隐蔽的是：把含 `node_modules` 的项目从 Windows 拷到 mac 后，`npm install` 会输出
`up to date` 然后**什么都不做**——npm 只比对版本号，不校验二进制平台。后果是
`.bin/` 下仍是 Windows 的 `.cmd`/`.ps1` 且丢失 Unix 可执行位，于是报
`sh: .../electron-vite: Permission denied`。因此 `scripts/setup-mac.sh` 强制
删除重装 + `electron-builder install-app-deps` 重编 + `chmod +x` 兜底。

### 4.4 设计令牌三层结构

全局样式重写为三层，避免面板各写一套内联样式导致深浅主题下不协调：

| 层 | 内容 | 例子 |
|----|------|------|
| 第一层 · 尺度 | 与主题无关的度量 | `--fs-micro…--fs-2xl`、`--sp-1…--sp-8`、`--r-xs…--r-pill`、`--control-h-sm/-h/-lg` |
| 第二层 · 语义色 | 随主题切换的语义变量 | `--bg-0/-1/-2`、`--bg-inset`、`--text-1/-2/-3`、`--border-subtle/-strong`、`--shadow-sm/md/lg`、`--titlebar-bg`、`--menu-bg` |
| 第三层 · 控件层 | 控件专用派生变量 | `--field-bg/-border/-h`、`--btn2-bg/-border/-text`、`--focus-ring` |

控件基础层用 `:where()` 选择器书写（特异性为 0，面板内联样式可自由覆盖）：
统一 `focus-visible` 焦点环、placeholder 颜色、`select` 自绘箭头并显式设置 `option` 配色
（否则 Windows 下深色主题的原生下拉会出现白底白字）、`number` 去掉步进箭头、
复选框用 `accent-color` 跟随主题、`prefers-reduced-motion` 下关闭过渡。

渲染层另有 `components/ui/tokens.ts` 提供控件样式原语
（`field / fieldSm / fieldMono / textarea / select / btnPrimary / btnSecondary / btnGhost / btnDanger / segment / chip / badge / surface / overlay / toolbar` 等），
19 个既有面板的内联样式已批量迁移到令牌：283 处字号、126 处圆角归入阶梯，
89 处 `1px solid var(--border)` 按语义分派为 field 边框 / 内凹容器 / 无边 chip / 卡片弱边框；
分段控件选中态统一改为 `--bg-2` + `--shadow-sm` 的「浮起」表达，深色下不再出现白框。

### 4.5 密度与缩放

密度（`data-density=compact|default|comfortable`）只改控件高度与内边距令牌，字号不变；
缩放走 preload 内的 `webFrame.setZoomFactor`（范围 0.7–1.6），字号与控件等比放大。
两者互相独立、各自持久化。

### 4.6 自绘下拉框与字号基准修正（M23 UI 轮）

本轮解决四个实测缺陷，根因都指向「把外观交给系统或交给单个面板」这一类做法。

**1）字号基准整档上移。** 原基准 `--fs-md: 13px` 是照桌面端英文 UI 的习惯定的，
但中文字形的视觉重心比拉丁字母低、笔画更密，同一 px 值下可读性明显更差；
再叠加高分屏常见的 125%/150% 非整数缩放，`--fs-micro: 10px` 的中文会直接糊掉。
因此整条阶梯上移一档：

| 令牌 | 旧 | 新 |
|------|----|----|
| `--fs-micro` | 10px | 11px |
| `--fs-xs` | 11px | 12px |
| `--fs-sm` | 12px | 13px |
| `--fs-md` | 13px | 14px |
| `--fs-lg` | 15px | 16px |
| `--fs-xl` | 18px | 20px |
| `--fs-2xl` | 22px | 24px |

行高同步放宽（`--lh-tight` 1.25→1.3、`--lh-normal` 1.5→1.55），
控件高度跟上一档（`--control-h` 30→32、`--control-h-sm` 24→26、`--control-h-lg` 36→38、
`--control-px` 10→11），三档密度的对应值一并上移，避免字变大而控件不变造成的挤压。

**2）原生 `<select>` 全量替换为自绘 `Select`。** 原生下拉展开后的候选列表由操作系统绘制，
CSS 只能改 `option` 的底色与字色，圆角、阴影、行高、内距、选中标记一律管不到；
Windows 深色主题下系统还会给列表额外描一圈边框，与应用其余浮层不是一套。
新组件 `src/renderer/src/components/ui/Select.tsx` 的两个关键决定：

- **列表用 portal 挂到 `body` 并按 `position: fixed` 定位。** 下拉框大量出现在
  `overflow: auto` 的面板与弹窗里，若列表是触发器的子元素就会被父容器裁切——
  这正是「下拉/输入框被遮挡」这类问题的共同根因。改 fixed 后须自行处理
  滚动与 resize 时重新贴位，以及下方空间不足时向上翻转。
- **选项超过 8 项自动出现搜索框。** 串口号、协议模板、环境变量这类列表会长到几十项。

交互细节：hover 与键盘光标用**底色**表达，当前选中值用**右侧勾选标记**表达——
两者走不同视觉通道，否则用户分不清「光标停在哪一项」与「当前生效哪一项」。
组件对外只放行布局类 `style`（宽度、flex、margin 等），外观一律由令牌决定；
需要破例时走显式的 `unsafeStyle`。这是因为迁移前十几个面板各写一份 padding 与 background，
下拉框长得一个样都没有，而这恰恰是要修的问题本身。

配套地，`components/ui/tokens.ts` 中的 `select` / `selectSm` 原语已删除，
不给后来者留一条「看起来合规」的错误路径。

**3）强选中态令牌。** 类型卡片等「被选中」的容器原先只换 `--selected-bg`，
深色下 7% 白叠加与 `--bg-2` 几乎分不出来。新增 `--selected-strong-bg` /
`--selected-strong-border`，选中态改为**底色 + 描边 + 字重**三通道同时表达，
图标块另做反色，弱对比环境下也能一眼看出。

**4）多行输入框最小高度。** WebSocket 自定义 Header 这类多行输入原先写死 `height: 54`，
两行示例文本就撑满。统一改为 `minHeight: 88` + `resize: vertical`，
并在 `textarea` 右下角用背景渐变画出对角线提示，告诉用户此处可拖高。

### 4.7 按钮层级重排与悬停反馈接线（M23 续）

**1）悬停 / 按下反馈此前完全失效。** `--btn-hover` / `--btn2-bg-hover` /
`--btn2-bg-active` 这几个令牌定义完就没有任何选择器引用，全项目按钮实际是「按下去没反应」。
根因是按钮外观走内联样式 `background: var(--btn-bg)`，而内联样式优先级高于任何 class 规则，
常规写法 `.btn:hover { background: ... }` 盖不住，只能靠 `!important` 或给 18 处按钮逐个加 class。

实际采用的做法是**就地重定义变量**：

```css
:where(button):not(:disabled):hover {
  --btn-bg: var(--btn-hover);
  --btn2-bg: var(--btn2-bg-hover);
  --btnq-bg: var(--btnq-bg-hover);
}
```

内联的 `var()` 是在元素自身上解析的，只要 hover 时把变量在该元素上改掉，
内联样式的取值就跟着变。一条规则覆盖全部按钮，不需要改任何组件代码，也不需要 `!important`。
输入框的 hover 用同一手法接上 `--field-bg-hover` / `--field-border-hover`。

**2）新增「柔和主操作」层级 `btnQuiet`。** 原先左栏「新建连接」与空态主按钮都用 `btnPrimary`，
即主题里对比度最高的样式。问题在浅色主题下最明显：深底白字的按钮压在浅灰半透明侧栏上、
紧邻右侧纯白内容区，割裂感很强；而它是常驻元素，做成最亮的东西会持续抢注意力。

按钮层级因此扩为四级：

| 层级 | 令牌 | 用途 | 深色 | 浅色 |
|------|------|------|------|------|
| 主操作 | `btnPrimary` | 一次性提交动作（创建 / 确定 / 发送） | 浅底深字 | 深底白字 |
| 柔和主操作 | `btnQuiet` | 常驻入口（新建连接、空态按钮） | 10% 白叠加 + 弱描边 + 投影 | 纯白 + 描边 + 投影 |
| 次级 | `btnSecondary` | 面板内普通动作 | 6% 白叠加，无描边 | 4.5% 黑叠加，无描边 |
| 三级 | `btnGhost` | 图标条、关闭按钮 | 透明，hover 才浮底 | 同 |

**3）工具箱页签不再用主按钮色。** 原 `tabActive` 用 `--btn-bg`，浅色下的深底白字页签
比页面里真正的确认按钮还醒目，层级反了。改为「浮起」表达（`--bg-0` 实底 + 弱描边 + `--shadow-sm`），
与分段控件的选中态保持同一套语言：导航类选中用浮起，动作类才用实色。

### 4.8 打包版屏蔽开发者工具（M29.1）

**要求**：交付给使用者的安装版不应该能开出 Chromium 开发者工具 —— 它会暴露内部实现与本地数据，误触后弹出的面板对非开发用户也只是困扰。

**为什么要三处一起关**：开发者工具有三条互不相通的入口。

| 入口 | 拦截位置 |
|------|---------|
| 顶部「帮助 → 开发者工具」菜单项 | 渲染层按 `devToolsEnabled` 条件渲染该菜单项 + 主进程 IPC 处理器直接返回 |
| `F12` / `Ctrl+Shift+I` / `Ctrl+Shift+J` / `Ctrl+Shift+C` | `webPreferences.devTools: false` + `webContents.on('before-input-event')` 显式吞掉按键 |
| 右键「审查元素」上下文菜单 | 同样由 `devTools: false` 关闭 |

只关一处，另两条照样能开出面板。

**实现要点（为什么这样做）**

| 决策 | 原因 |
|------|------|
| 判据用 `app.isPackaged`，不用自定义环境变量 | 环境变量能被用户在启动时覆盖，等于没锁。`isPackaged` 由 Electron 依据是否运行在 asar 内判定，装出来的应用无论怎么起都是 `false` |
| 开关通过 `additionalArguments` 同步传给 preload，不走异步 IPC | 渲染层首帧就要决定菜单里显不显示这一项。走 IPC 会先画出来再抹掉，闪一下比没有更像故障 |
| 菜单项用数组展开条件插入，而不是 `disabled: true` | 一个永远点不动的灰项对使用者没有信息量，只会让人反复去点 |
| 保留 `before-input-event` 拦截，不只依赖 `devTools: false` | 不同 Electron 版本对这些组合键的处理并不一致，显式吞键才在所有版本上行为一致 |
| 渲染层 `F12` 分支在打包版**不吃按键**（直接 return） | 交给主进程统一拦，避免出现「按了有反应但没面板」的错觉 |
| IPC 处理器保留但静默返回 | IPC 通道对渲染层始终可达，界面隐藏入口不等于通道关闭。这是兜底 |

**副作用**：`F12` 从快捷键一览与 README 快捷键表中移除。开发运行（`npm run dev`）不受影响，一切照旧。

## 5. 数据模型（关键实体）

- **Session**：id、kind、name、config、status、metrics、createdAt、autoStart、group（分组名，空=未分组）、tags（字符串数组，主进程侧 trim+去重）。
- **Frame**：id、sessionId、direction(TX/RX/system)、peerId、ts、rawBytes、encoding、text、size、level（系统消息级别）、conn（是否连接生命周期日志）。
- **HttpLogEntry**：id、sessionId、ts、method、path、query、status、durationMs、reqHeaders、reqBody、respHeaders、respBody、matchedRoute、scenario（命中时生效的场景名）。
- **SessionConfig · UDP 字段（M29）**：`udpBindHost`、`udpBindPort`（本地绑定，客户端 0 = 系统随机）、`udpBroadcast`、`udpMulticastGroup`、`udpTtl`、`udpReuseAddr`、`udpPeerIdleMs`（服务端对端空闲淘汰，0 = 不淘汰）。**刻意不复用 `host`/`port`**：客户端需同时表达「默认目标」与「本地绑定」，挤在一组字段上必然语义打架。UDP 会话不写 `framing`。
- **Snippet**：id、name、group、format、content、appendTerminator。
- **MockService**：id、name、port、tls、basePath、cors、routes[]、activeScenarioId、state（有状态内存数据集）。
- **MockRoute**：id、method、pathPattern（精确/通配 `*`/`:param`/正则）、matchQuery、matchHeader、matchBody、priority、respStatus、respHeaders、respBody、bodyType、delay、mode（template|script）、scriptRef、enabled。
- **HttpMockScenario**：id、name、note、overrides（`Record<routeId, HttpScenarioOverride>`，字段级覆盖）、fault（可选，覆盖全局故障注入）。`HttpMockConfig` 持有 `scenarios[]` 与 `activeScenarioId`，随会话一起落盘到 workspace.json。
- **KindCaps / KIND_CAPS（M28.1）**：每种 `ConnectionKind` 的能力开关 `{ protoTemplate, terminator, encodingSwitch, frameMock, recording, loopSend, peerTarget, topicPublish, pointTable, subscription, alertRule }`。定义在 `app/meta.ts`，是纯常量不进 store；会话界面、命令面板、规则应答面板都读它决定渲染什么。
- **ProtoTemplate**：id、name、kinds（M28.1 新增，适用的连接类型数组，空=通用模板；旧数据缺该字段按通用处理）、matchPrefixHex（仅解析该 HEX 前缀开头的报文，空=不限）、direction（any|tx|rx）、checksum（none|sum8|xor8|crc16-modbus）、fields[]。存于渲染层 localStorage `toolbox.protoTemplates`，会话与模板的绑定存 `toolbox.protoSelection`（值为空=关闭、`auto`=按前缀自动匹配、其余为模板 id）。
- **ProtoField**：id、name、type（uint8/16/32、int8/16/32、float32/64、hex、ascii、bcd、bits）、length（变长类型的字节数，0=吃掉剩余）、bigEndian、scale、offset、unit、enumMap（`0=关机,1=运行`）、note、chart（勾选后该数值字段绘制曲线）。
- **RecordingFile**：`{ format: 'flowprobe-recording'（读取时兼容旧标识 `debug-toolbox-recording`）, version: 1, sessionName, sessionKind, startedAt, durationMs, note, frames: RecordedFrame[] }`。落盘为 `.json`，版本化以便后续兼容。
- **RecordedFrame**：offsetMs（相对录制起点的毫秒偏移，而非绝对时间戳）、direction、encoding、rawBase64、text、size、peerLabel、level、conn。回放时以 `baseTs + offsetMs` 还原为 Frame 并置 `replay: true`。
- **Series / SeriesPoint**：解析结果按字段名聚合成 `{ name, unit, points: [{ ts, value }] }`。抽取只扫描最近 1000 条报文，且仅在曲线面板打开时执行；`value` 取工程值换算后（枚举映射前）的数字，因此枚举字段不会污染曲线。
- **HttpScenarioOverride**：enabled、respStatus、bodyType、respBody、respHeaders、delayMs、mode、script，均为可选；未设置即表示不覆盖。
- **SessionMetaPatch**：`{ group?: string; tags?: string[] }`。经 `session:setMeta` 传入，只更新组织信息并落盘，不触碰适配器。
- **LayoutState 的 editorH（M28.1）**：发送区高度（像素，夹在 96–560），随 `toolbox.layout` 落盘。之所以不放组件 state：切会话/切标签会重挂组件，用户拉出来的高度会回到默认值。
- **SessionOrg（渲染层本地态）**：`{ collapsed: string[]; tagFilter: string[] }` 存 localStorage `toolbox.sessionOrg`；keyword 仅内存态。
- **Bucket（看板）**：`{ ts, txBytes, rxBytes, txFrames, rxFrames }`，ts 已按 stepMs 对齐；空桶显式补零。
- **LatencyStat**：`{ count, min, max, avg, p50, p95 }`，来自 HttpLogEntry.durationMs 排序后取分位。
- **Slice / SizeBin / GroupStat**：看板环图切片、长度分档、分组累计，均为纯函数产出，不进 store。
- **HttpRequest**：id、name、method、url、query[]、headers[]、bodyType、body、auth、timeout、followRedirects。
- **Collection**：id、name、folders[]、requests[]、variables[]。
- **Environment**：id、name、variables（键值，如 baseUrl、token）。
- **Assertion**：id、requestId、target（status|time|jsonPath|text|regex|schema）、operator、expected。
- **HistoryConfig**：enabled（落库总开关）、retentionDays（保留天数，0=不按时间清理）、maxFrames（报文条数上限，0=不限）、storePayload（是否连原始字节一起存）。存于历史库 meta 表，与 workspace.json 分离——它描述的是库自身的行为，不属于会话配置。
- **HistoryFrameRow**：id、sessionId、sessionName、sessionKind、sessionGroup、ts、direction、size、encoding、rawBase64、text、peerLabel、level、conn。会话快照字段在写入时冗余，删除会话后仍可读。
- **HistoryHttpRow**：id、sessionId、sessionName、ts、method、path、query、status、durationMs、reqBody、respBody、matchedRoute、scenario。
- **HistoryQuery / HistoryHttpQuery**：筛选条件对象（会话集合、时间区间、方向/状态码族、关键字、字节数或耗时下限、limit/offset、排序）。
- **HistoryPage<T>**：`{ rows: T[], total: number }`，total 用于分页控件。
- **HistoryStats**：enabled、frames、httpLogs、sessions、fileBytes、oldestTs、newestTs、byDay[]、bySession[]、path。
- **历史库位置**：Windows `%APPDATA%\\flowprobe\\history.db`（含 `-wal`/`-shm` 附属文件），与 workspace.json 同目录。
- **WindowState**：`{ maximized: boolean; fullScreen: boolean; focused: boolean }`。主进程在 `maximize/unmaximize/enter-full-screen/leave-full-screen/focus/blur` 事件里推给渲染层，自绘标题栏据此切换按钮图标。注意事件必须逐个 `w.on(...)` 注册——用数组循环注册会因 Electron 的重载签名导致 TS 类型不匹配。
- **AppInfo（M33 精简）**：`{ name, version, platform, arch, userData, workspacePath, historyPath }`。用于「关于」面板与「打开数据目录」，路径由主进程给出，渲染层不拼路径。**已去掉 `electron` / `chrome` / `node` 三个字段**：这三项对使用者没有可操作性，而无人消费的 IPC 字段迟早腐烂成「不知道谁在用、不敢删」。
- **MqttConfig（M22）**：`{ url, clientId, username, password, keepalive, cleanStart, protocolVersion: 4|5, connectTimeout, reconnect, tls?: { ca, cert, key, rejectUnauthorized, servername }, will?: { topic, payload, qos, retain }, subscriptions: MqttSubscription[] }`。
- **MqttSubscription（M22）**：`{ id, filter, qos: 0|1|2, enabled, nl?, rap?, rh? }`（后三项为 MQTT 5 的 No Local / Retain As Published / Retain Handling）。随会话落盘。
- **MqttPublishOptions（M22）**：`{ topic, qos, retain, contentType?, responseTopic?, correlationData?, userProperties?: Record<string,string> }`。MQTT 报文映射为 Frame 时把 `topic/qos/retain/packetId` 放入 `meta`，因此历史与搜索无需改表。
- **ModbusConfig（M22）**：`{ transport: 'tcp'|'rtu'|'rtu-over-tcp', host?, port?, serial?: SerialConfig, unitId, timeoutMs, retries, gapMs, wordOrder: 'be'|'le', byteOrder: 'be'|'le', points: ModbusPoint[] }`。字序与字节序独立可配——工控设备在 32 位量的排列上分歧极大，写死必然踩坑。
- **ModbusPoint（M22）**：`{ id, name, func: 1|2|3|4, addr, quantity, type: 'uint16'|'int16'|'uint32'|'int32'|'float32'|'float64'|'bits'|'string', scale, offset, unit, writable, pollMs, enabled, note, chart }`。`chart` 勾选后该点位数值进入数值曲线，复用 M15 的序列抽取。
- **ModbusReadPlan（M22）**：轮询前把同 `func` 且地址相邻（间隔 ≤ `mergeGap`，默认 8）的点位合并成批量读请求 `{ func, startAddr, quantity, points: ModbusPoint[] }`，单请求数量上限按功能码约束（线圈 2000、寄存器 125）。合并的目的是把 N 个点位的 N 次往返压成少数几次。
- **ModbusException（M22）**：`{ code, name, message }`，覆盖 `0x01`–`0x0B`，界面直接显示中文原因而非裸码。
- **TabState（M25）/ SplitState（M27）**：标签态 `{ ids: string[]; previewId: string | null }` 存 `toolbox.tabs`；分屏态 `{ splitId, splitRatio, focusPane }` 并入 `toolbox.layout`。两者都在渲染层 localStorage，不进 workspace.json——它描述的是「窗口摆放」，换机器不该跟着走。
- **DiffPick / DiffResult（M27）**：`DiffPick = { sessionId, sessionName, frameId, ts, direction, size, rawBase64 }`，最多两条，带会话信息才能跨会话对比；`DiffResult = { cells: { kind: 'same'|'replace'|'left-only'|'right-only', left?: number, right?: number }[], sameCount, replaceCount, leftOnlyCount, rightOnlyCount, degraded }`。**比的是 `rawBase64` 解出的原始字节，不是已解码文本**——文本解码会把不可打印字节折叠成同一个替代字符，差异就消失了。`degraded` 表示超出 LCS 预算已退化为逐位置比较。HEX 视图与字段表视图共用同一份 cells。
- **TimeSyncState（M27）**：`{ enabled, source: 'left'|'right'|null, ts, token }`。**刻意不持久化**——它描述的是此刻两侧滚到哪儿，重启没有意义；且每次滚动都在变，落盘会把滚动变成磁盘写。
- **HistoryContextQuery（M23 规划）**：`{ sessionId, ts, id, before, after }`，从历史库取命中行前后各 N 条，用于搜索结果回跳的上下文时间轴。
- **RouteDraft（M28）**：由 Mock 请求日志推断出的路由草稿 `{ key, method, pattern, samplePath, count, status, bodyType, body, respHeaders, params, varied, sourceIds }`。`key = method + pattern` 作去重键；`varied` 表示同一模式出现过不同响应体（分页接口很常见，提醒用户改脚本模式）；`sourceIds` 保留参与合并的日志 id 便于回溯。路径推断：纯数字段、UUID、≥16 位 hex 段转参数，参数名取前一段的单数形式 + `Id`，重名加序号。
- **MonitorTask（M28.2）**：`{ id, name, requestIds, envId, intervalSec, enabled, delayMs, stopOnFail, notify, failThreshold, lastRunAt?, lastPassed?, failStreak? }`。`requestIds` 为空表示「集合全部」——这样后续往集合里加接口会自动纳入巡检，不必回来改任务；`intervalSec` 最小 10 秒；`failStreak` 成功即归零，供「连续失败 N 次才通知」判定。
- **MonitorRun（M28.2）**：`{ id, taskId, taskName, startedAt, totalMs, ran, stepPass, stepFail, assertTotal, assertPass, failures: [{ name, status, detail }] }`。**只留失败摘要而非完整响应**：历史保 200 条，存全量响应体会迅速把 localStorage 撑爆，而排查时真正需要的是「哪个接口的哪条断言没过」。
- **RunResult / RunStep / RunStats（M28.2）**：`runCollection.ts` 的产物，手动批量运行与定时巡检共用同一份结构与同一个 Markdown 渲染函数，避免两套报告格式。
- **AlertRule（M28.3）**：id、name、enabled、sessionId（null=按 kinds 生效）、kinds、direction（any|tx|rx）、source（field|text|checksum）、templateId（`auto`=按前缀自动匹配）、field、op（gt/gte/lt/lte/eq/ne/between/outside/contains/notContains/regex）、value、value2、severity（warn|error）、highlight、notify、stopSession、cooldownSec、hits、lastFiredAt。存 localStorage `toolbox.alertRules.v1`。
- **AlertEvent（M28.3）**：id、ruleId、ruleName、severity、sessionId、sessionName、frameId、ts、direction、detail（人话触发说明，如「温度 82.4 ℃ > 80 ℃」）、snapshotHex（截断到 64 字节）、snapshotText。存 localStorage `toolbox.alertEvents.v1`，上限 300 条。
- **FrameAlert（M28.3）**：`{ ruleId, ruleName, severity, detail }`，作为 `Frame.alert` 的渲染层注解。**主进程不产生该字段**——告警依赖协议解析模板，而模板是渲染层的用户数据，放到主进程要多同步一份状态。
- **AlertRule（M28 规划）**：`{ id, sessionId, templateId, field, op: 'gt'|'lt'|'eq'|'ne'|'between', value, value2?, action: { highlight, notify, stopSession } }`；命中产出 `AlertEvent { id, ruleId, sessionId, ts, actual, frameSnapshot }`，汇总进告警中心。
- **TlsCertInfo（M29.2）**：`{ ok, reason?, subject, issuer, selfSigned, validFrom, validTo, daysLeft, altNames[], fingerprint256, keyMatch? }`。由主进程 `inspectCert` 产出，**只回摘要不回私钥正文**，界面拿到的信息足以判断可用性但不足以泄露密钥。`SessionConfig` 侧新增 `tlsCertPath` / `tlsKeyPath` 仅用于界面展示落盘位置，服务真正读的是 `tlsCert` / `tlsKey` 正文（避免文件被移动后服务突然起不来）。
- **ModbusSlaveRegion（M29.1）**：`{ id, name, area: ModbusArea, start, count, initial, readOnly, enabled, animate: none|ramp|sine|random|toggle, periodMs, min, max, step }`。位区（0x/1x）的初值与动画范围由界面自动夹到 0/1，避免存下一个协议上不可能的配置。
- **ModbusSlaveConfig（M29.1）**：`{ transport: tcp|rtuOverTcp|rtu, host, port, unitId, acceptAnyUnitId, maxConnections, regions[], responseDelayMs, dropRate, forceException }`。串口参数复用 `SessionConfig` 顶层既有的串口字段，不再单开一套。
- **ModbusSlaveRegionValues（M29.1）**：`{ regionId, values: number[] }[]`，随 `SessionEvent.modbusSlaveValues` 增量推送，只带真正变化过的区。**渲染层刻意不做本地乐观更新** —— 值能不能落下取决于该地址是否已声明，先行显示会给出与真实状态相反的反馈。
- **FrameMark（M29.1）**：`{ id, sessionId, sessionName, sessionKind, frameId, ts, direction, size, snapshotHex, snapshotText, note, createdAt }`。存 localStorage `toolbox.frameMarks.v1`，上限 500 条、`snapshotHex` 截断 128 字节。**刻意存快照而不是仅存 `frameId`**：报文缓冲是内存态，清屏或重启后只有 ID 的书签就成了点不开的空行。
- **LocateRequest（M29.1）**：`{ sessionId, frameId, token }`，`useMarks` 里的一次性定位信号。`token` 单调递增，因此连续点同一条书签也能重复触发滚动（布尔标志第二次点时值不变，effect 不会重跑）。
- **HarEntryInput（M29.1）**：`{ startedAt, timeMs?, method, url, reqHeaders?, reqBody?, status, statusText?, respHeaders?, respBody?, respBodyBase64?, respSize?, comment? }`。各来源把自己的行映射成这个最小形状，再由 `shared/har.ts` 的 `toHarEntry` 补齐 HAR 1.2 的全部必填字段。**刻意不让各来源直接构造 `HarEntry`**：必填字段有二十来个，各自拼必然漏，而漏字段的后果是 DevTools 拒绝整份文件。
- **HistoryItem 的响应摘要（M29.1）**：接口测试历史新增 `statusText` / `respHeaders` / `respBody` / `respSize` / `respTruncated`。`respBody` 截断到 `HISTORY_BODY_LIMIT = 8192` 字符，截断标记会写进 HAR 的 `comment`。旧版本存下的历史缺这些字段，导出时同样在 `comment` 里注明，不静默给出空响应。
- **UpdateState（M31）**：`{ phase, currentVersion, newVersion?, releaseNotes?, releaseDate?, percent?, transferred?, total?, bytesPerSecond?, error?, checkedAt? }`。`phase` 取 `idle|unconfigured|checking|available|downloading|downloaded|up-to-date|error`，**刻意做成单个扁平枚举而不是多个布尔量**：这几种状态互斥，布尔量组合会产生「既在下载又已是最新」这类不可能态。进度三个量只在 `downloading` 阶段有值。
- **UpdateSettings（M31 → M33 收缩）**：`{ autoCheck, autoDownload }`，存 `userData/update.json`（**与 workspace.json 分开**：工作区会导出给同事，这两个开关是本机个人偏好）。M31 版本另有 `kind` / `feedUrl` / `githubRepo` / `githubProxy` 四个字段，M33 全部移除 —— 更新地址改由打包时的 `publish.url` 唯一决定（理由见 §3.32）。读取旧配置文件时那四个字段被静默丢弃，不做迁移也不报错。
- **更新地址来源（M33）**：不再有拼接函数。地址取自安装包内的 `app-update.yml`（由 `electron-builder.yml` 的 `publish.url` 生成），主进程只手工解析其中的 `url:` 一行，用于识别占位域名与界面展示；实际请求由 electron-updater 读同一个文件自行发起，因此不调用 `setFeedURL()` —— 同一个地址有两个来源时，两处不一致的排查成本极高。
- **PerfSample（M31 规划）**：`{ ts, frameMs, ipcRttMs, sqliteQueue, bufferCount, heapUsed }`，按秒采样保留最近 10 分钟，仅在性能面板打开时采集。
- **Preset / Workspace**：连接配置、片段、Mock 服务/路由、接口集合与环境的集合，JSON 导入导出。
- **GlobalSearchQuery**：keyword、scanLimit（0=全部历史，默认 50000）、perKind（每类返回上限）、sessionIds（可选限定）、from（可选起始时间）。
- **SearchHit**：kind（frame|http）、id、sessionId、sessionName、sessionKind、ts、snippet、matchAt、matchLen、direction、size、method、status、path。`matchAt`/`matchLen` 供界面行内高亮，避免渲染层再跑一遍匹配。
- **GlobalSearchResult**：keyword、frames[]、https[]、frameTotal、httpTotal、bySession（会话聚合计数）、scanned（实际扫描行数）、elapsedMs、truncated（是否被 perKind 截断）。
- **PersistedWorkspace（落盘结构，v1）**：`{ version: 1, savedAt: number, sessions: PersistedSession[] }`；`PersistedSession = { id, kind, name, config, autoStart, group, tags, createdAt }`。位置：Windows `%APPDATA%\debug-toolbox\workspace.json`、macOS `~/Library/Application Support/debug-toolbox/workspace.json`、Linux `~/.config/debug-toolbox/workspace.json`。读取失败或格式异常时降级为空工作区，不阻塞启动。

## 6. 非功能需求

- **性能（已实现虚拟滚动与合批）**：单会话高吞吐下 UI 不卡。报文区与 Mock 请求日志采用变高虚拟滚动，只渲染可视区行并缓存实测行高；渲染层用 requestAnimationFrame 把高频事件合批入库，避免逐帧重渲染；内存缓冲上限 5 万条（超出丢弃最旧）。实测 2 万条报文时行节点约 20-30 个，滚动帧耗时与空闲基线一致。看板侧的桶聚合从最新报文倒序回扫、遇窗口外即停，并按 1 秒节拍重算，把图表刷新频率与报文吞吐解耦。历史落 SQLite 已实现（WAL + 200 条/800ms 批量事务写入，查询前 flush，按天与按条数双重清理）。
- **稳定**：IO 全在主进程，异常隔离到会话级别，单会话崩溃不影响其他会话。
- **跨平台**：Windows / macOS / Linux；串口依赖 prebuilt 二进制。
- **安全**：`contextIsolation` 开启、禁用 `nodeIntegration`、脚本沙箱、证书本地存储加密。
- **可测试**：适配器层单元测试 + Mock 引擎回归用例。
